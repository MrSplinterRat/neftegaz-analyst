# 🛢 AI-агент «Нефтегазовый аналитик»

Агент в роли старшего аналитика нефтегазового рынка: отвечает на профильные
вопросы, опираясь на базу отраслевых отчётов, дополняет их веб-поиском,
прогнозирует цены на нефть собственным расчётным модулем — и в каждом ответе
показывает, откуда взята каждая цифра.

---

## Быстрый старт

### Docker (одна команда)

```bash
docker build -t neftegaz-analyst .
docker run -p 8501:8501 -v "$PWD/data:/app/data" neftegaz-analyst
```

Интерфейс: <http://localhost:8501>

### Локально

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # при необходимости укажите свой LLM

python scripts/fetch_prices.py    # история цен Brent (yfinance)
python scripts/fetch_reports.py   # корпус отчётов EIA STEO
python scripts/build_index.py     # векторный индекс

streamlit run ui/app.py
```

### Подключение своей LLM

Система работает с любым OpenAI-совместимым endpoint. По умолчанию —
локальный сервер, поэтому проект запускается вообще без ключей:

```bash
# хостовая модель
OPENAI_BASE_URL=https://api.openai.com/v1
OPENAI_API_KEY=sk-...
LLM_MODEL=gpt-4o

# или локальный llama.cpp
llama-server -m model.gguf --host 127.0.0.1 --port 8081
```

```

   вопрос ────────────►│    route     │  классификация запроса
                       └──────┬───────┘
              ┌───────────────┼────────────────┐
              ▼               ▼                ▼
      ┌──────────────┐ ┌────────────┐  ┌───────────────┐
      │  out_of_scope│ │  forecast  │  │   retrieve    │  ← RAG по отчётам
      └──────┬───────┘ └─────┬──────┘  └───────┬───────┘     ВСЕГДА ПЕРВЫЙ
             │               │                 │
             │               │        достаточно?│ нет / нужна актуальность
             │               │                 ▼
             │               │         ┌───────────────┐
             │               │         │      web      │  ← дополнение
             │               │         └───────┬───────┘
             │               ▼                 ▼
             │        ┌─────────────────────────────┐
             │        │           answer            │  синтез + маркировка
             │        └──────────────┬──────────────┘
             └───────────────────────┴────────────► ответ
```

Граф написан явными узлами (`neftegaz/agent/graph.py`), а не отдан
универсальному tool-calling циклу. Причина в требовании 2.4: приоритет
источников — это **предписанная политика**, и проверяющий должен иметь
возможность прочитать её в коде и сверить с ТЗ построчно. Когда политика живёт
внутри усмотрения модели, проверить её нельзя — можно только надеяться.

# Краткий отчёт: решения, ограничения, планы

## Какие решения приняты и почему

### Приоритет источников — в коде, а не в промпте

Требование 2.4 задаёт конкретный порядок: сначала отчёты, веб — как дополнение.
Это реализовано условными переходами графа (`_after_retrieve`), а не просьбой к
модели соблюдать порядок. Промпт можно проигнорировать, ребро графа — нельзя.
Веб включается ровно в двух случаях: корпус вернул меньше половины ожидаемых
фрагментов, либо вопрос содержит маркер актуальности («сейчас», «текущий»,
«последние»). Второе условие важно отдельно: отчёты выходят раз в месяц и на
вопрос «какая цена сегодня» не ответят при любом качестве поиска.

### Маркировка — по абзацам, а не по ответу

Ссылка ставится на каждое утверждение, а не одна в конце. В комбинированном
ответе единая ссылка молча распространила бы авторитет проверяемого отчёта на
непроверяемую веб-часть. Формат жёсткий: `[Отчёт OPEC MOMR, март 2025, с. 14]`
против `[Источник: Reuters, web]`. Отсутствие обязательного поля вызывает
исключение, а не подстановку умолчания: выдуманный номер страницы делает
непроверенное утверждение выглядящим проверенным — это худшее, что может
сделать этот модуль.

### Чанкинг сквозной, с запоминанием страницы каждого символа

Страницы склеиваются в один поток, параллельно ведётся массив «страница
каждого символа». Чанк может пересекать разрыв страницы и честно сообщает
`page_start` и `page_end`. Альтернатива — резать каждую страницу отдельно —
проще, но рвёт предложения на каждом разрыве. Пустые страницы (схемы, сканы)
сохраняются как пустые записи: выбросить их означало бы сдвинуть нумерацию
всех последующих, а ссылка на неверную страницу хуже отсутствия ссылки.

### Выбор компонентов — по критерию «проверяется без регистрации»

| Компонент | Выбор | Почему |
|---|---|---|
| Веб-поиск | DuckDuckGo (`ddgs`) | Единственный из списка ТЗ без API-ключа: проверяющий клонирует репозиторий и видит работу, не регистрируясь |
| Эмбеддинги | fastembed / ONNX, многоязычная модель | Корпус заказчика не покидает машину; без torch образ легче примерно на 2 ГБ. ★Многоязычность обязательна: отчёты на английском, вопросы на русском — поиск кросс-языковой по построению |
| Векторная БД | Qdrant, встроенный режим | Из списка ТЗ; пишет в каталог, отдельный сервис поднимать не нужно — отсюда запуск одной командой |
| Цены | yfinance (`BZ=F`) | Прямо назван в ТЗ, не требует ключа. Stooq отпал: закрылся proof-of-work проверкой браузера |
| Корпус | EIA STEO, 8 выпусков | Из трёх названных в ТЗ агентств (ОПЕК, МЭА, EIA) только EIA отдаёт PDF напрямую — см. ограничения |
| LLM | любой OpenAI-совместимый endpoint | Умолчание локальное, поэтому система работает без ключей; заказчик подставляет свой |

### Фильтр жёлтой прессы — списком, а не суждением модели

Требование 2.3 просит отфильтровать часть жёлтой прессы. Это сделано явным
deny-list плюс предпочтением известных отраслевых и агентских доменов. Список
можно прочитать, оспорить и поправить под свою редакционную политику; мнение
модели о достоверности источника — нельзя. Список намеренно короткий:
длинный спекулятивный отсеивал бы законные источники, а для аналитика это
более дорогая ошибка, чем пропуск одного таблоида. Неизвестные домены
проходят, но ранжируются ниже известных.

### Два метода прогноза, разные по природе

- **Экспоненциальное сглаживание** — написано вручную, без зависимостей,
  работает всегда и проверяется построчно. Точечный прогноз плоский: у модели
  уровня нет трендового члена. Это свойство метода, а не дефект, и именно
  поэтому доверительный интервал здесь важнее линии.
- **ARIMA(1,1,1)** — из statsmodels, умеет тренд и автокорреляцию.
  Одно дифференцирование, потому что уровень цен нестационарен.

Режим `auto` берёт ARIMA и откатывается к сглаживанию, если подгонка не
удалась — на коротком или вырожденном ряде это нормальный исход, а ответ
пользователю всё равно нужен.

### Сценарий по предложению — эластичность названа явно

Пересчёт «сокращение добычи на N млн барр./сут → изменение цены» использует
коэффициент 10% на 1 млн барр./сут (`PRICE_ELASTICITY` в
`tools/forecast_tool.py`). Краткосрочная эластичность спроса на нефть по цене
оценивается примерно в −0.05…−0.10, что при мировом предложении около
102 млн барр./сут даёт 10–20% на 1 млн барр./сут; взят консервативный край.
Число вынесено в константу с обоснованием в комментарии именно для того, чтобы
с ним можно было спорить: на нём держится вся сценарная ветка.

## Ограничения текущей реализации

1. **Корпус — только EIA.** ОПЕК отдаёт MOMR через форму (прямой запрос
   получает HTTP 403), IEA OMR — платный продукт. Скрипт загрузки честно об
   этом пишет; оба источника добавляются вручную копированием PDF в
   `data/reports/` с соблюдением конвенции имени. Архитектура их поддерживает,
   ограничение — в доступе, не в коде.

2. **Сценарный пересчёт линеен.** Одна константа эластичности одинаково
   действует на любом горизонте и при любой величине шока. Реальная реакция
   цены асимметрична (сокращение действует сильнее наращивания) и зависит от
   уровня запасов. Модель отказывается считать при шоках, выводящих множитель
   за границу разумного, вместо того чтобы напечатать отрицательную цену.

3. **Прогноз не учитывает факторы спроса и предложения.** Обе модели работают
   только с историей цены. Регрессия по факторам (запасы OECD, дисциплина
   ОПЕК+, промышленное производство) в ТЗ упомянута как один из вариантов и не
   реализована — данные по факторам требуют отдельных источников с ключами.

4. **Качество ответа определяется подключённой LLM.** Логика приоритизации,
   поиск и расчёты работают одинаково, но формулировка ответа и точность
   переноса чисел из фрагментов зависят от модели. На слабой локальной модели
   ссылки иногда оформляются неточно.

5. **Кросс-языковой поиск на облегчённой модели.** Умолчание
   (`paraphrase-multilingual-MiniLM-L12-v2`, ~0.5 ГБ) выбрано ради быстрого
   первого запуска. На русских запросах к английскому корпусу
   `intfloat/multilingual-e5-large` заметно точнее — переключается одной
   строкой в `.env`, ценой ~2.2 ГБ и примерно четырёхкратного времени
   индексации.

6. **Нет постоянной памяти диалога.** Каждый вопрос обрабатывается независимо;
   уточняющие вопросы вида «а что по второму пункту» не поймут контекста.

## Что улучшили бы при наличии большего времени

**В первую очередь — то, что меняет качество ответов:**

1. **Переранжирование (cross-encoder reranking).** Векторный поиск возвращает
   top-k по близости эмбеддингов; переранжировщик перечитывает эти k фрагментов
   вместе с запросом и переупорядочивает. На отчётах с большим количеством
   похожих таблиц это обычно даёт больший прирост, чем смена модели эмбеддингов.

2. **Гибридный поиск: плотный + BM25.** Нефтегазовые запросы полны точных
   идентификаторов — «Urals», «MOMR», «bcf/d», номера кварталов. Лексический
   поиск находит их надёжнее векторного; объединение результатов двух методов
   покрывает и терминологию, и смысл.

3. **Извлечение таблиц из PDF.** Сейчас таблицы попадают в текст как
   расползшийся набор чисел. Разбор их в структуру (`camelot`, `pdfplumber`)
   позволил бы отвечать на количественные вопросы точными цифрами из ячеек,
   а не пересказом.

4. **Регрессия по факторам спроса и предложения** как третий метод прогноза,
   с подключением рядов запасов и добычи из EIA API.

**Во вторую — эксплуатация:**

5. **Память диалога** (LangGraph checkpointer) и уточняющие вопросы.
6. **Кэш ответов веб-поиска** с временем жизни: одинаковые запросы в течение
   дня не должны каждый раз ходить в сеть.
7. **Оценочный набор**: 30–50 вопросов с эталонными ответами и метрикой
   «доля утверждений с корректной ссылкой» — чтобы изменения в промптах и
   параметрах поиска мерились, а не обсуждались.

**Отдельно — по производительности предобработки.** Разбор PDF и чанкинг
детерминированы, упираются в CPU и тривиально распараллеливаются. На корпусе в
сотни отчётов это становится узким местом холодного старта, и здесь уместен
перенос именно этой функции в нативную реализацию за тем же интерфейсом
(так устроены `polars`, `tokenizers`, `pydantic-core`). Мы сознательно не
делали этого в рамках задания: система должна была остаться полностью
питоновской и сдаваемой целиком, а оптимизация без замера на реальном объёме
была бы украшением, а не инженерией.

## Об использовании Ouroboros

В названии задания стоит вопрос, где нужно использовать Ouroboros. Отвечаем
прямо: **в этой поставке он не использован.**

Мы рассматривали его как среду разработки — инструмент, которым пишется код, —
и на оценке скорости увидели, что в отведённое время развернуть цикл
самоперестраивающегося агента, обеспечить его изоляцию и получить
предсказуемый результат не успеваем. Выбор был между работающим продуктом,
соответствующим ТЗ, и экспериментом с неопределённым исходом. Мы выбрали
продукт.

Отдельно о встраивании Ouroboros **в рантайм** конечного решения. Это
возможно, но стоит существенно больше человеко-дней, чем есть в задании, и не
из-за объёма кода: обеспечить предсказуемое поведение у конечного пользователя
для системы, спроектированной как инструмент разработчика, — самостоятельная
инженерная задача. Для регулируемой отрасли, где ответ аналитика должен быть
воспроизводим и проверяем, компонент, переписывающий сам себя между запусками,
требует отдельного контура контроля.

Направление считаем рабочим и намерены к нему вернуться — на горизонте, где
под него есть время и внятный контур изоляции.
