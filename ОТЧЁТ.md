# Отчёт о реализации: AI-агент «Нефтегазовый аналитик»

Развёрнутый ответ на пункты 4.4 и 4.5 технического задания: какие решения
приняты и почему, какие у реализации ограничения, что было бы сделано при
большем запасе времени.

Документ написан для инженера, который будет читать код, и потому построен
вокруг замеров и компромиссов. Выбор библиотеки почти ничего не говорит о
качестве системы; выбор между двумя работающими вариантами, сделанный по
замеру, говорит почти всё.

Корпус, на котором получены все приведённые числа: 8 выпусков EIA Short-Term
Energy Outlook (декабрь 2025 — июль 2026), 469 страниц, 9474 индексируемых
фрагмента.

## 2. Архитектура

Агент собран как граф на LangGraph:

```
                    ┌─► retrieve ─┬─► answer ──► END
START ─► route ─────┼─► web ──────┘
                    ├─► forecast ──► answer ──► END
                    └─► out_of_scope ────────► END
```

Шесть узлов: маршрутизация, поиск по отчётам, веб-поиск, расчёт, синтез
ответа, отказ вне компетенции. Узел `retrieve` условно переходит либо сразу к
ответу, либо в веб — если найденного мало.

**Маршрутизация живёт в коде.** Это первое решение и самое важное для отрасли,
где ответ должен быть воспроизводим. Требование 2.4 описывает порядок работы с
источниками; в системном промпте соблюдение этого порядка становится
вероятностным. Модель может выполнить инструкцию, может и не выполнить, и
отличить одно от другого получится лишь по конечному ответу.

Поэтому переход в веб сделан ребром графа с проверяемым условием: если по
отчётам получено меньше половины запрошенных фрагментов, управление уходит в
веб. Запрос на прогноз распознаётся структурно, до обращения к модели, по
горизонту и величине шока в тексте вопроса. У модели остаётся ровно то, что она
делает лучше кода: формулировка ответа из уже отобранного материала.

Побочная выгода — отладка. Когда система отвечает не тем, журнал показывает, на
каком ребре она свернула; догадываться, что модель «подумала», не приходится.

## 3. Принятые решения

### 3.1 Маркировка по абзацам

Требование 2.4 просит явно указать, откуда какая информация. Минимальное
исполнение — подпись под ответом с перечнем источников. Оно бесполезно: в
ответе, собранном из отчёта и веба, читателю нужно знать происхождение каждого
отдельного утверждения, а перечень прочитанного этого не даёт.

Поэтому маркер стоит после каждого утверждения, и маркеры разного рода
различаются по форме:

```
[Отчёт EIA STEO, июль 2026, с. 35–36]
[Источник: Investing.com, web]
[Расчёт: ARIMA(1, 1, 1) + сценарий предложения, горизонт 90 дн.]
```

Расчёт намеренно не оформляется как отчёт: у него нет ни даты публикации, ни
страницы, и пустые поля в шаблоне отчёта выдали бы вычисленное за
процитированное. Источник иного рода получает собственную форму метки.

### 3.2 Чанкинг сквозной, с памятью о странице каждого символа

Ссылка обязана указывать страницу. Простое решение, резать каждую страницу
отдельно, этой задачи не создаёт, но рвёт предложения на каждом разрыве, а в
отчётах STEO абзацы через разрывы идут постоянно.

Реализовано иначе: страницы склеиваются в один поток символов, параллельно
ведётся массив «страница каждого символа». Фрагмент может пересекать разрыв и
честно сообщает `page_start` и `page_end`.

Две детали, которые легко упустить:

* Страницы склеиваются без разделителя. Любой разделитель — это текст,
  которого нет ни на одной исходной странице; он попал бы внутрь фрагментов
  и внутрь смещений, по которым мы потом отчитываемся.
* Пустые страницы (схемы, сканы) сохраняются как пустые записи. Выбросить их
  значило бы сдвинуть нумерацию всех последующих, а ссылка на неверную
  страницу хуже отсутствующей.

Умолчания — 1200 знаков с перекрытием 200. Компромисс: достаточно крупно,
чтобы фрагмент нёс законченное рассуждение вместе с числами, достаточно мелко,
чтобы эмбеддинг представлял одну тему и не усреднял несколько.

### 3.3 Поиск гибридный: смысл и слова, слитые по местам

Отчёты STEO наполовину состоят из таблиц, а строка таблицы выглядит так:

```
United States ................................ 13.28 13.51 13.78 13.77 …
```

Из слов у неё — название страны. Эмбеддеру нечего сближать с русским вопросом
«какая добыча нефти в США», и замер это подтвердил. По чистой векторной
близости нужная строка стояла на 99-м месте: косинус 0.64 против 0.752 у лидера
выдачи. Разрыв такой величины не закрывается настройкой ранжирования:
настраивать нечего.

Поэтому поиск идёт двумя способами сразу, векторным по смыслу и BM25 по словам,
а выдачи сливаются по местам (Reciprocal Rank Fusion). Складывать веса напрямую
здесь нельзя: косинус лежит в узкой полосе около 0.7, вес BM25 не ограничен
сверху и зависит от длины запроса, так что сложение молча назначило бы курс
обмена между несопоставимыми шкалами. Место в списке безразмерно, и складывать
места законно. Смягчитель фузии выбран большим (60), чтобы согласие двух разных
способов весило больше, чем уверенность одного.

**Условие, без которого затея провалилась бы молча.** Корпус английский,
вопросы русские — у запроса «добыча нефти в США» с английской строкой таблицы
нет ни одного общего слова, и BM25 честно вернул бы пустоту. Отказ был бы не
виден: выдача просто осталась бы прежней. Поэтому в `neftegaz/rag/keyword.py`
есть словарь предметной области (22 гнезда терминов), сопоставляющий по началу
русского слова, потому что русский склоняется. Латиница проходит насквозь для
смешанных вопросов вроде «прогноз Brent».

Замер по эталону — строке `United States` из таблицы `Table 3d. World Crude Oil
Production`:

| запрос | только вектор | только слова | гибрид |
|---|---|---|---|
| «Какая добыча нефти в США?» | 11-е место | 1-е | **1-е** |
| `United States crude oil production…` | не в рассматриваемом списке | 1-е | **2-е** |

Векторный поиск в одиночку не доставал эталон ни разу.

Цена: индекс BM25 строится за 0.21 с один раз на процесс, запрос занимает
0.08 с, пик памяти процесса — 371 МБ вместе с моделью эмбеддингов. Новых
зависимостей реализация не добавляет: только стандартная библиотека.

Эталон опознаётся по содержанию фрагмента; номер страницы для этого не годится.
На одной странице лежит несколько фрагментов, и совпадение страницы засчитало бы
попаданием соседа. Так первая редакция замера дала завышенный результат, пока
критерий не был ужесточён.

### 3.4 Заголовок таблицы отдельным полем

Продолжение таблицы — это фрагмент вида `20.31 20.51 20.97 20.49 …`, в котором
нет ни одного слова. Его эмбеддинг — шум: запрос «добыча нефти в США» не может
к нему приблизиться, потому что сближать не с чем. Отсюда и брался ответ
«данных по добыче в США нет» при том, что данные есть.

Лечение — дать числам имя: заголовок ближайшей таблицы выше по тексту.
Ключевая деталь в том, куда его положить. Заголовок хранится в отдельном поле
`context` и никогда не вклеивается в `text`, потому что `text` обязан дословно
совпадать с тем, что стоит на странице отчёта. Иначе цитата перестаёт быть
проверяемой, а проверяемость и есть предмет поставки. В вычислении
эмбеддинга участвует пара «заголовок + текст», в цитате — только текст.

Заголовок берётся не любой: не дальше 8000 знаков назад. Таблица STEO
занимает одну-две страницы, за этим пределом ближайший заголовок относится уже
к другой таблице. Чужой заголовок хуже отсутствующего — он не просто не
поможет найти фрагмент, он привяжет числа к чужой таблице.

Заголовок получили 1250 из 1962 оконных фрагментов (64%).

### 3.5 Строки таблиц — отдельными фрагментами

Даже с заголовком строка про США оставалась внутри фрагмента на 1200 знаков
вместе с десятком других стран и сносками. Мешает здесь разбавление: строка про
США составляет пятую часть фрагмента, остальное — про другие страны. Способ
поиска на это не влияет.

Поэтому строки таблиц индексируются дополнительно к оконным фрагментам.
Строка опознаётся по точкам-выноске: в сплошной прозе три точки подряд
встречаются лишь многоточием, а за многоточием не идут пять чисел подряд.
Граница подписи — последнее число предыдущей строки; вариант «ближайшая
заглавная буква» даёт обрубок (у строки `Natural gas (dollars per million Btu)`
ближайшая заглавная — это `B`, и подписью становится `Btu)`).

Одно и то же место отчёта оказывается в индексе дважды, в двух разрешениях, и
это замысел: окна нужны прозе, строки нужны числам. Индекс вырос с 1962 до 9474
фрагментов; 7512 строк, из них 79% несут заголовок своей таблицы. Сборка
занимает 12 минут 36 секунд, пик памяти 1.4 ГБ.

Сама по себе эта правка целевой задачи не решила: строки появились в индексе, но
в первую пятёрку не попали, потому что векторная близость их всё равно не
вытягивала. Работать она начала только вместе с поиском по словам (3.3).
Структура оказалась необходима и недостаточна.

**Строка едет в индекс парами «столбец = значение».** Раньше вместе со строкой
хранились два независимых списка — названия столбцов отдельно, числа отдельно, —
и связать третье число с третьим столбцом должна была модель, считая их по
порядку. Это то самое выравнивание по счёту, которое мы запретили себе при
разборе страницы: связь значения с колонкой обязана быть прочитана из
расположения, а не выведена из порядка (3.4). Требовать этого от своего кода и
оставлять модели — непоследовательно, а цена ошибки та же: сдвиг на один столбец
даёт настоящее число не за тот период, ответ выглядит обычным, и проверить его
можно только вернувшись к странице — а он для того и нужен, чтобы туда не
возвращаться. Вместо двух списков строка разбирается в явные пары:

```
United States: Q1 = 12.94, Q2 = 13.27, Q3 = 13.27, Q4 = 13.45, Q1 = 13.28, …,
               2024 = 13.23, 2025 = 13.61, 2026 = 13.53
```

Пары строятся только при точном равенстве числа значений числу столбцов.
Никакого выравнивания по левому краю и отбрасывания лишних: неравные длины
означают, что либо шапка чужая, либо строка неполная, и любая пара тогда была бы
выдумкой. Пустой результат — законный исход, при нём остаётся прежнее поведение:
заголовок таблицы без шапки колонок. Прочерк при этом остаётся прочерком:
«Q3 = -» значит «данных за третий квартал нет», и это утверждение, а не пропуск;
молча выбросив прочерки, мы сдвинули бы все последующие значения — та же ошибка,
только изнутри.

Пример показывает и границу приёма. В таблицах STEO квартальные обозначения
идут тремя одинаковыми четвёрками, а годы, к которым эти кварталы относятся,
стоят отдельной строкой выше и шапкой не признаются: слов в ней вчетверо меньше,
чем значений в строке, а неравные длины мы отвергаем. Пара поэтому называет
квартал, но не год; додумать год за отчёт значило бы вернуть ту самую догадку по
порядку, ради устранения которой всё это и сделано.

Пары лежат в поле `context`, рядом с заголовком таблицы, и в `text` не
вклеиваются: `text` обязан дословно совпадать со страницей отчёта, иначе цитата
перестаёт быть проверяемой. Отвечающая модель получает пары отдельной строкой
рядом с фрагментом.

### 3.6 Шкала оси графика как признак «данных нет»

Ранжирование поощряет фрагменты с высокой плотностью цифр — там данные. Но под
это описание попадают три разных класса: глоссарий (цифр мало, данных нет),
подпись к графику (цифр много, данных нет) и таблица (цифр много, данные есть).
Три класса не упорядочиваются по одной оси, и вес тут крутить бесполезно: нужен
второй признак, разделяющий два верхних класса.

Им служит арифметическая прогрессия: метки оси Y (`11.5 12.0 12.5 13.0 13.5`)
образуют прогрессию, сам ряд значений — нет. Два исключения обязательны:
годы (целые в диапазоне 1900–2100) и нумерация строк (целые с шагом 1).

Результат: подписей к графикам в первой пятёрке выдачи было 4, стало 0.

Отвергнутый по дороге вариант стоит упомянуть, потому что он выглядел
убедительно: ограничить величину поправки долей разброса оценок в выдаче.
Замер его опроверг: глоссарии вернулись на первые места. Диагноз «поправка
больше сигнала» был правдоподобен и неверен. Признак не различал того, что
должен был различать, и вес тут ни при чём.

### 3.7 Приёмка файла: что известно о PDF до того, как поверить прочитанному

PDF — это контейнер, и «сломан» он бывает по-разному: файл может быть обрезан
при выкачке, может нести правки, дописанные в конец поверх прежней версии, а
может быть безупречен по структуре и при этом отдавать не те символы. Первые
два случая видит любая проверка целости. Третий не видит ни одна: текст
извлекается, выглядит текстом, и отличить его от верного не по чему.

Поэтому перед индексированием файл проходит осмотр — `neftegaz/rag/intake.py`,
одна точка входа `inspect_pdf`. Она возвращает отчёт и не поднимает исключений:
любой сбой, включая отсутствие внешнего инструмента и его таймаут, становится
находкой с устойчивым кодом. Молчание было бы неотличимо от «проверка не
запускалась», а это разные вещи.

Ступень файла — худшая из достигнутых:

| Ступень | Что означает |
|---|---|
| `OK` | контейнер цел, признаков неверного чтения не найдено |
| `NOTICE` | читается, но есть что знать: шрифты без таблицы `ToUnicode`, пустые страницы, дописанные ревизии |
| `WARN` | читается частично, либо два пути дают разный результат |
| `BROKEN` | контейнер нарушен: чтение возможно только режимом восстановления |
| `UNKNOWN` | проверку выполнить не удалось — статус неизвестен |

`UNKNOWN` вынесен в отдельную ступень намеренно. Если бы невыполненная проверка
приравнивалась к чистой, удаление внешнего инструмента с машины улучшало бы
приёмку всего корпуса разом.

Проверяется четыре вещи. По байтам, без библиотеки: сигнатура `%PDF-` в первом
килобайте, `%%EOF` в последних четырёх килобайтах (его отсутствие — самый частый
след усечения при выкачке), число ревизий, последний `startxref` и то, стоит ли
по указанному им смещению таблица ссылок или объект. Через `pdfinfo` — число
страниц, причём жалоба в поток ошибок при нулевом коде возврата считается
находкой: poppler чинит многое молча и сообщает об этом только туда. Через
`pdffonts` — шрифты без `ToUnicode`; такой шрифт декодируется в другие символы, и
никакая проверка целости этого не показывает. Наконец, собственный путь чтения:
сколько страниц он видит и сколько из них без текста; расхождение с `pdfinfo` по
числу страниц означает, что как минимум один из двух неверен.

**Результат на корпусе** (8 выпусков EIA STEO, 469 страниц):

| Что | Сколько файлов |
|---|---|
| ступень `NOTICE` | 8 из 8 |
| ступень `OK`, `WARN`, `BROKEN` или `UNKNOWN` | 0 |
| находка «шрифты без `ToUnicode`» | 8 |
| находка «инкрементальные ревизии» | 2 |

Корпус структурно чист: ни одного обрыва, ни одной сломанной таблицы ссылок.
При этом сверка путей чтения (3.8) на этих же файлах расходится на 137 страницах
из 469. Два числа рядом и составляют довод в пользу отдельного модуля приёмки:
целость контейнера и верность чтения — разные свойства, и проверка первого
ничего не говорит о втором.

Приёмка сообщает, но не решает. Файл с находками всё равно индексируется:
выбор «брать или не брать» принимает тот, кто разворачивает систему, а дело
приёмки — чтобы находка не потерялась молча. Находки уровня файла едут дальше и
попадают в оговорки к фрагментам (3.9).

### 3.8 Сверка путей чтения: три читателя, четыре исхода

У одного извлекателя нет способа узнать, что он ошибся. Отказ, о котором идёт
речь, тихий: на выходе текст, текст похож на текст, кода ошибки нет. Дешёвый
свидетель против такого отказа один — второй путь чтения, устроенный иначе.
Там, где два пути согласны, ошибиться могут только оба сразу; там, где
расходятся, неверен как минимум один, и это место надо назвать.

Путей три (`neftegaz/rag/crosscheck.py`):

| Имя | Чем читает | Как собирает текст |
|---|---|---|
| `poppler` | `pdftotext -layout` | по операторам содержимого, колонки восстанавливаются эвристикой |
| `pdf2xml` | `pdftotext -bbox-layout` | по координатам слов на странице; **это текст, который ложится в индекс** |
| `pypdf` | собственный код на Python | по операторам содержимого, о колонках не знает |

**Независимость здесь частичная, и границу надо назвать вслух.** Первые два
пути — один и тот же исполняемый файл poppler и один и тот же декодер глифов.
Различаются они тем, что делают после декодирования, поэтому свидетельствуют
только о сборке: порядок чтения, склейка соседних чисел, потерянная колонка. К
искажению самого декодирования они слепы одинаково: если таблица `ToUnicode`
шрифта врёт, оба пути соврут согласованно и дадут «согласны». Ровно поэтому
добавлен третий: `pypdf` разбирает поток содержимого и раскодирует глифы своим
кодом, не разделяя с poppler ни строки. Расхождение с ним свидетельствует ниже
сборки. Но и это не превращает согласие в доказательство: сверка ловит
расхождение путей, а не истину. Чем независимее пути, тем шире класс отказов,
который она делает громким, — не более того.

Сравниваются числа, а не текст. Для аналитика содержание отчёта — цифры; слово
с опечаткой стоит несравнимо дешевле, чем цифра из соседней колонки. Основная
мера — мультимножество числовых токенов страницы, и она же бесплатно разделяет
четыре исхода:

| Исход | Что наблюдалось | Что это значит |
|---|---|---|
| `AGREE` | те же числа в том же порядке | пути согласны |
| `ORDER` | те же числа, другой порядок | расходится порядок чтения; данные на месте, неверна их привязка |
| `TOKENIZE` | те же цифры, другое членение (`20242024` вместо двух `2024`) | расходятся границы токенов |
| `DIVERGE` | цифры разошлись | число потеряно или декодировано не тем шрифтом |

Складывать это в одну «похожесть» значило бы стереть разницу между
«переставлено» и «утрачено», а лечатся они разным.

**Результат на корпусе:**

| Файл | Страниц | `AGREE` | `ORDER` | `TOKENIZE` | `DIVERGE` | Токенов расходится |
|---|---|---|---|---|---|---|
| EIA STEO 2025-12 | 56 | 39 | 0 | 0 | 17 | 94 |
| EIA STEO 2026-01 | 58 | 40 | 0 | 1 | 17 | 72 |
| EIA STEO 2026-02 | 62 | 45 | 0 | 1 | 16 | 70 |
| EIA STEO 2026-03 | 57 | 39 | 0 | 1 | 17 | 70 |
| EIA STEO 2026-04 | 60 | 43 | 0 | 1 | 16 | 71 |
| EIA STEO 2026-05 | 60 | 43 | 0 | 0 | 17 | 75 |
| EIA STEO 2026-06 | 60 | 44 | 0 | 1 | 15 | 85 |
| EIA STEO 2026-07 | 56 | 39 | 0 | 0 | 17 | 79 |
| **Всего** | **469** | **332** | **0** | **5** | **132** | **616** |

Ноль в столбце `ORDER` читать буквально нельзя. Вердикт страницы — худший из
попарных, поэтому ноль означает не «порядок нигде не разошёлся», а «ни на одной
странице расхождение порядка не оказалось самым тяжёлым из наблюдавшихся»:
страница, где два позиционных пути разошлись порядком, а третий вдобавок
разошёлся цифрами, попадает в `DIVERGE`.

Отдельно оговорено, о чём вправе судить пара с `pypdf`. Он выдаёт текст в
порядке операторов и о колонках ничего не знает, поэтому его «другой порядок» —
не находка, а устройство. Для пар с непозиционным читателем от вердикта
остаётся один вопрос, на который такой читатель отвечает лучше всех: те же ли
это цифры. Иначе признак загорался бы почти на каждой странице и заглушал те,
что несут сведения.

**Расхождение чаще всего адресно.** Когда путей три, можно спросить не только
«кто-то неправ», но и «кто именно»: путь, разошедшийся с обоими остальными
сильнее, чем те двое между собой, назван виновником. На корпусе виновник найден
на 109 страницах из 137 расходящихся — 83 раза это `pypdf`, 26 раз `pdf2xml`.
Разбор части страниц первой группы показал причину: `pypdf` видит подписи осей
на графиках, которые поплеровские пути передают иначе — теряют или склеивают в
один токен (`20262026` вместо двух `2026`). На таких страницах два поплеровских
пути сходятся между собой заметно лучше, чем каждый из них с `pypdf`: третий
путь приносит числа из графиков, которых в нашем тексте нет вовсе. Что из этого
следует для цитаты — в 3.9.

Сверка, как и приёмка, тотальна: читатель, который не ответил, не ждётся и не
подменяется, а выбывает с примечанием; при менее чем двух ответивших сказано,
что сверка не выполнена.

### 3.9 Как фрагмент был прочитан — часть ссылки

Ссылка обещает проверяемость: откройте страницу 35 и увидите то же самое.
Обещание держится настолько, насколько мы уверены, что прочли эту страницу
верно. Если два пути чтения дали на ней разные цифры, умолчать об этом значит
выдать спорное за проверенное.

Мера приписывается фрагменту, а не документу. Документ целиком почти никогда не
бывает хорошим или плохим: в наших выпусках 332 страницы из 469 читаются
одинаково, а на 132 пути расходятся по цифрам. Статус, приписанный файлу, у
первой же страницы становится ложью в одну из двух сторон — либо порочит чистые
страницы, либо покрывает грязные.

Ступеней четыре, и различаются они тем, чем подтверждено чтение
(`neftegaz/rag/confidence.py`):

| Ступень | Чем подтверждено | Что печатается в ссылке |
|---|---|---|
| `direct` | пути прочли страницу одинаково | ничего |
| `geometry` | цифры те же, расходится их порядок или членение; привязка чисел к заголовкам держится на нашей сборке по координатам, а не на согласии путей | `текст собран по геометрии страницы` |
| `disputed` | пути расходятся по цифрам | `⚠ два пути чтения расходятся по цифрам` |
| `unchecked` | сверка не выполнялась | `сверка чтения не выполнялась` |

У чистой ссылки метка остаётся чистой — иначе оговорка на спорной перестанет
бросаться в глаза. Готовая ссылка выглядит так:

```
[Отчёт EIA STEO, июль 2026, с. 35; ⚠ два пути чтения расходятся по цифрам]
```

`unchecked` — ступень, а не синоним `direct`, по той же причине, по которой в
приёмке есть `UNKNOWN`: если бы непроверенное молча считалось чистым,
отключение сверки повысило бы качество всех цитат сразу.

**Виновник расхождения меняет вердикт, но только в одну сторону.** Ступень
отвечает на вопрос, можно ли верить тому тексту, который лежит в индексе, а это
не то же самое, что «на странице кто-то читает иначе». Правило такое: если
расхождение сведено к одному пути и это не наш путь, страницу судят оставшиеся,
а расхождение выезжает оговоркой с именем пути; если виновник — наш путь,
ступень понижается по худшему; если виновника нет, берётся худший вердикт.
На корпусе это 83 страницы первого рода и 26 второго. Без такого правила
спорными пришлось бы объявить все страницы с графиками, хотя разобранные нами
числа на них никто не оспорил.

Находки приёмки едут вместе со ступенью и не понижают её. Шрифты без
`ToUnicode` — свойство файла, а не страницы: риск неверного декодирования
одинаков на согласных и на расходящихся страницах, и смешивать «этот фрагмент
прочтён спорно» с «весь документ несёт известный риск» нельзя — это разные
утверждения с разными последствиями. В нашем корпусе такая оговорка стоит у
фрагментов всех восьми файлов.

Фрагмент, перешедший границу страниц, получает худшую ступень из покрытых: у
цитаты одна метка, и она отвечает за весь приведённый текст.

Ступень проставляется при индексировании, а не при ответе. К моменту ответа
файла уже нет под рукой — есть только фрагмент из индекса, и если статус не
уехал вместе с ним, восстановить его будет неоткуда. Поэтому ступень и оговорки
лежат в полезной нагрузке точки, возвращаются вместе с найденным фрагментом
(`Hit.confidence`, `Hit.caveats`) и попадают в заготовку утверждения, из которой
`neftegaz/tools/citations.py` собирает ссылку.

**Кто дописывает метку в текст ответа.** Текст ответа пишет модель, и ссылки в
нём она ставит сама по заданному в промпте формату. Ступень ей при этом не
показывается: пересказчик вправе счесть оговорку неважной и потерять её — молча
и не всегда, то есть ровно та подмена, против которой сам механизм и сделан.
Поэтому готовый ответ проходит через `annotate_answer` из
`neftegaz/tools/citations.py`: код находит в тексте ссылки на отчёты,
сопоставляет каждую с фрагментами, которые действительно были поданы модели в
контекст, дописывает метку внутрь ссылки и один раз в конце ответа объясняет,
что читателю с ней делать. Тем же соображением — «оговорку дописывает код, а не
модель» — в системе уже отдана коду приписка о недоступной базе отчётов.

Ссылка, накрывающая несколько фрагментов, получает худшую из их ступеней: у
цитаты одна метка, и она отвечает за весь приведённый по ней текст. Ссылка,
которую не накрыл ни один поданный фрагмент, метки не получает вовсе —
«прочитано напрямую» по умолчанию заверило бы непроверенное, — но считается
отдельным числом: она означает, что модель сослалась на то, чего не читала, и
это отказ другого рода, чем спорная страница.

**Что дало включение.** На пяти демонстрационных сценариях — 25 ссылок на
отчёты; пометку получили 2 (обе на страницах, где пути чтения расходятся по
цифрам), 23 остались чистыми, мимо поданных фрагментов не пришлась ни одна.
Отрицательный контроль проверялся в обе стороны и закреплён тестами: тот же
ответ на спорных фрагментах обязан выглядеть иначе, а на чистых — остаться
дословно прежним. Первое доказывает, что метка не декоративна; второе — что мы
не пометили всё подряд, отчего пометка перестала бы что-либо различать.

**Те же числа видны в интерфейсе, и это проверено на живом ходе, а не только
тестами.** Панель «⚙️ Настройки» открывается строкой о том, чем на самом деле
был заполнен контекст последнего вопроса: сколько знаков ушло на отчёты (и
сколько фрагментов подано из скольких найденных), сколько на историю разговора,
на веб и на расчётный модуль, — каждое число рядом со своим бюджетом. Ниже
стоят числа разметки: сколько в ответе ссылок на отчёты, сколько из них с
пометкой о чтении и сколько пришлось мимо поданных фрагментов. До первого
вопроса на этом месте написано, что здесь появится, — то есть пустая панель
отличима от сломанной.

Проверка на экране поймала настоящую ошибку, и в этом её ценность. Прогон велся
с подставной моделью, отвечающей заранее известным текстом со ссылкой на
страницу, которой в поданных фрагментах не было. Панель назвала это вслух:
«⚠ ссылок мимо поданных фрагментов: 1». Показатель различает ссылку на
прочитанное и ссылку на выдуманное — ровно то, ради чего он заведён.

### 3.10 Одинаковый вход — одинаковый индекс и одинаковый порядок выдачи

Идентификатор фрагмента выводится из его содержания: имя источника, дата
отчёта, вид фрагмента, страницы, смещение в потоке и дословный текст
склеиваются в ключ, от которого берётся `uuid5` с постоянным пространством имён
(`neftegaz/rag/store.py`). Раньше здесь стояло случайное число (`uuid4`), и из
этого следовали три вещи.

Первая: две сборки индекса по одному корпусу давали разные идентификаторы, то
есть утверждение «тот же вход — тот же индекс» было неправдой, а сравнить две
сборки было нечем. Вторая: повторная загрузка того же отчёта не заменяла
прежние фрагменты, а добавляла их копии — прежние остались бы в индексе
навсегда под своими случайными идентификаторами, отсюда и привычка пересобирать
корпус с нуля. Третья: при равных оценках порядок выдачи надо чем-то разрешать,
а случайный идентификатор для этого не годится.

Равные оценки развязываются явно, в обеих ветвях поиска: сначала по оценке, при
её равенстве — по ключу из содержания (дата, источник, страница, вид, текст).
Сортировка в Python устойчива, то есть сохраняет входной порядок при равенстве
ключей, но это помогает лишь тогда, когда входной порядок сам устойчив; порядок
точек с одинаковым косинусом хранилищем не оговорён. На слиянии двух ветвей
равенство ещё вероятнее: оценка RRF складывается из мест в двух списках и
принимает мало разных значений, так что совпадения там обычное дело.

Отказ, который этим закрыт, ничего не роняет и не ловится проверкой одного
прогона: два одинаково близких фрагмента просто меняются местами, и на тот же
вопрос приходит другая цитата — правдоподобная, из того же отчёта, с той же
оценкой. Увидеть подмену можно, только сравнив два прогона между собой, а
объяснить её пользователю нечем.

Чего этот ключ не даёт — хронологии. Поле даты хранит название месяца
по-русски («июль 2026»), и сравнение строк ставит июль раньше июня: это
алфавит, а не время. Для устойчивости порядка этого достаточно, для
осмысленного «свежее раньше» — нет; понадобится хронология, в полезную нагрузку
придётся положить сортируемую дату.

### 3.11 Три метода прогноза, разные по природе

ТЗ требует минимум двух методов. Реализованы ARIMA(1,1,1), простое
экспоненциальное сглаживание и модель по балансу рынка. У них разная природа, и
виднее всего это в том, откуда каждый берёт доверительный интервал.

* **ARIMA** строит собственный доверительный интервал из структуры модели.
  Одно дифференцирование — потому что уровень цены не стационарен, а её
  приращения близки к тому.
* **Экспоненциальное сглаживание** даёт интервал из остатков и служит запасным
  путём: если подгонка ARIMA не сходится, система не падает, а отвечает
  методом попроще и сообщает, каким именно — вместе с причиной, по которой
  запасной метод понадобился.
  ★Коэффициент сглаживания подбирается по ряду, а не берётся общепринятым
  умолчанием 0.3. Замер на поставляемом ряде Brent (1827 наблюдений):
  одношаговая ошибка при 0.3 — 2.54 долл./барр., при подобранном 0.94 — 1.89,
  на четверть меньше. Подбор при этом упирается в верхнюю границу, и это не
  дефект, а свойство данных: дневная цена близка к случайному блужданию, для
  которого лучший прогноз на шаг вперёд — последнее наблюдение. Границы
  оставлены именно поэтому — иначе метод перестал бы сглаживать вовсе.
  ★★Главное здесь не ошибка, а КАЛИБРОВКА, и проверялась она не той сигмой, из
  которой строится коридор, а попаданиями: доля случаев, когда факт через 30
  дней оказывался внутри 95% интервала, построенного по данным до этого
  момента, — 97.7% при 0.3 и 95.2% при подобранном. То есть прежний коридор
  был шире номинального, а новый совпал с ним; сужение здесь — не потеря
  осторожности, а исправленная калибровка.
* **Модель по балансу рынка** берёт интервал из двух источников сразу: остатка
  собственной регрессии и измеренной ошибки чужого прогноза факторов. Подробно
  о ней — в §3.13; она единственная из трёх не экстраполирует ряд цены, а
  выводит цену из добычи и запасов.

Все три возвращают точечный прогноз, 95% интервал и краткую интерпретацию. В
интерпретацию намеренно вынесено расширение полосы с горизонтом: на 90 днях она
раскрывается с 10.33 до 102.55 долл./барр. Это главное, что аналитик должен
понимать про дальний прогноз: точечная оценка на далёком горизонте несёт
несопоставимо меньше сведений, чем на ближнем.

Интерпретация пишется по-русски, как и весь остальной вывод расчётного модуля.
Абзац был английским, и это оставалось единственным местом расчётного блока,
где текст доходил до читателя не напрямую, а пересказом языковой модели — то
есть через того самого посредника, от которого расчёт отгорожен ровно затем,
чтобы числа не пересказывались. Перевод чисел не коснулся: те же данные дают
те же значения до сотых. У метода уровня в абзаце добавилась строка о том, что
плоская линия прогноза — свойство метода, а не дефект расчёта; у методов с
трендом её нет, потому что там она вводила бы в заблуждение.

★Попутно исправлено следствие, которое перевод сделал бы дефектом: решение
«нужно ли второе мнение» принималось по английской подстроке в НАЗВАНИИ метода,
то есть по тексту, написанному для человека. Перевод названия сломал бы это
решение молча — факторный прогноз стал бы спрашивать второе мнение у самого
себя. Природа метода вынесена в отдельное типизованное поле; название осталось
подписью для читателя и на поведение больше не влияет.

**★Интервал строится в логарифмах цены — и это не деталь реализации.** Первая
версия обоих методов работала в уровнях: `точка ± z·σ·√h` у сглаживания,
собственный интервал в долларах у ARIMA. Ширина такого интервала растёт как
корень из горизонта без всякой границы, а цена ограничена снизу нулём — и
модель печатала ОТРИЦАТЕЛЬНУЮ цену: −1.98 долл./барр. на годе и −119.54 на
пяти годах у сглаживания, −33.06 на пяти годах у ARIMA. Дефект не был виден ни
из кода, ни из тестов: он виден только из выхода, и открылся при сквозном
прогоне на длинных горизонтах.

Лечение — не обрезание по нулю, которое исправило бы печать и оставило неверной
саму ширину, а правильная форма: интервал строится на логарифме цены и
возвращается в уровни экспонентой (геометрическое броуновское движение —
стандартная модель для цены актива). Границы положительны по построению, а
интервал асимметричен: вверх цена может уйти в разы, вниз только до нуля.
Побочно снята и вторая неверность — модель в уровнях считала дисперсию шага
одинаковой при цене 20 и при цене 120, тогда как колеблется цена процентами.

★Отдельная находка того же прохода. Подгонка ARIMA по голому логарифму
обрывалась на ПЕРВОЙ итерации с `converged=False` — не бросая исключения, то
есть режим `auto` этого не замечал и возвращал числа, выглядящие как обычный
ответ. На той же серии, умноженной на 100 (лог-доходность в процентах),
подгонка сходится за 14 итераций; множитель 1000 разваливает её в переполнение,
так что масштаб выбран замером. Сходимость теперь едет в `params` результата,
и на неё есть тест.

Решение о вызове модуля принимает не модель: горизонт и величина шока
распознаются в тексте вопроса структурно, до обращения к LLM.

### 3.12 Сценарий по предложению — кривая спроса названа явно

Запрос «оцени диапазон цен при сокращении добычи на N млн барр./сут»
пересчитывается по кривой спроса с постоянной эластичностью. Если спрос
описывается как `Q = A · P^ε`, то, чтобы рынок поглотил сдвиг предложения, цена
обязана сместиться на `P₁/P₀ = (1 + ΔQ/Q₀)^(1/ε)`, где `Q₀` — мировое
предложение (102 млн барр./сут), а `ε` — эластичность спроса по цене.

Первая версия использовала линейный коэффициент: 10% изменения цены на 1 млн
барр./сут. Три его свойства были ложными, и все три лечит одна правильная
функция:

- **Он ломался на больших шоках.** Множитель `1 − share·10` обращался в ноль при
  шоке в 10% мирового предложения, и модуль отказывался считать — ровно там, где
  вопрос интереснее всего. Степенная форма определена всюду, где предложение
  остаётся положительным; отказ остался только на физической границе `ΔQ ≤ −Q₀`.
- **Он был симметричен.** Сокращение и наращивание на одинаковый объём двигали
  цену одинаково по модулю. На степенной кривой сокращение на 2 млн барр./сут
  даёт +21.9%, наращивание тех же 2 млн — −17.6%; асимметрия возникает из формы,
  а не из отдельного допущения.
- **Он игнорировал горизонт.** Недельный и годовой прогноз сдвигались одинаково.
  Теперь `ε` интерполируется между краткосрочной оценкой (−0.10 на квартале) и
  долгосрочной (−0.30 на пяти годах): за месяцы потребитель почти не может
  изменить поведение, за годы может.

На малых шоках обе формы совпадают, поэтому калибровка первой версии не
потеряна: ±1 млн барр./сут даёт −9.3% / +10.4% против −9.8% / +9.8%. Это
закреплено тестом — замена формы не должна была тихо поменять ответ.

Коридор после сценария РАСШИРЯЕТСЯ, а не просто сдвигается. Сценарий добавляет к
прогнозу гипотезу об эластичности, а гипотеза не может сузить незнание:
центральная линия идёт по нашей оценке `ε`, граница со стороны более сильного
отклика — по краю литературного диапазона. Прежняя версия умножала весь кадр на
одно число, то есть утверждала, что добавленное допущение ничего не стоит.

Все параметры кривой вынесены в конфигурацию, а не оставлены в коде: вся
сценарная ветка стоит на допущениях, которых нет в наших данных, и рецензент
должен иметь возможность не согласиться, не трогая модуль. По той же причине
допущение едет ВМЕСТЕ с ответом — в тексте сценария печатаются доля мирового
предложения, множитель, принятое значение `ε`, горизонт и прямая оговорка, что
это оценка из литературы, а не измерение на наших данных.

#### Вилка сценария: «с 2 до 3 млн барр./сут» считается по обоим концам

Аналитик редко называет одно число. «Что будет, если ОПЕК+ сократит добычу
с 2 до 3 млн барр./сут» — обычная форма вопроса, и раньше система отвечала на
неё одним из двух неудачных способов. На записи через «с … до» она переспрашивала,
считая вилку непрочитанным сценарием. А на записи через тире («2–3 млн барр./сут»)
и через «от … до» — молча брала ОДИН конец и выдавала обычный расчёт.

Замер до правки на семи реалистичных формулировках: три давали переспрос, три
читались одним концом без единого слова об этом, одна (вилка процентов) —
переспрос. Второе хуже первого: ответ выглядит нормальным, а посчитан по
условию, которого человек не называл.

Теперь вилка читается диапазоном. Оба конца считаются от одного и того же
базового прогноза, и отчёт печатает результат парой:

```
Прогноз на конец горизонта: 98.78 — 102.03 долл./барр. (со сценарием,
множитель уже учтён) — вилка сценария, по одному числу на каждый её конец
95% доверительный интервал: 67.08 — 158.59 долл./барр.
Сценарий: сокращение предложения от 2.00 до 3.00 млн барр./сут (2.0…2.9%
мирового предложения…) ⇒ множители к цене ×1.066 (ближний конец) и ×1.101
(дальний).
```

Три решения внутри стоит назвать отдельно, потому что каждое можно было принять
иначе.

**Коридор объединяется, а не усредняется.** Границы берутся крайние из двух
прогонов. Вилка — это незнание величины допущения, и объявить его серединой
значило бы выдать незнание за оценку: середины вилки человек не называл.

**Дальний конец считается от базы, а не от уже сдвинутого прогноза.** Иначе
множители перемножились бы, и получился бы сценарий «сначала сокращение на 2,
потом ещё на 3», которого никто не задавал. Это тот же класс ошибки, что однажды
уже стоил нам 101.98 вместо 97.21 (ниже, «Что нашёл сквозной прогон», пункт 4),
только совершённый бы
кодом, а не читателем. Проверка сравнивает вилку не со своей формулой, а с двумя
отдельными прогонами того же кода — своя формула ошиблась бы вместе с ним.

**Вилка ищется вплотную перед числом с опознанной единицей, а не по всему
вопросу.** Это снимает целый класс ложных срабатываний, из которого один
случай был живым: «что с ценой с 2024 до 2026 года при сокращении на 1,5 млн
барр./сут» прежнее правило объявляло вилкой ВЕЛИЧИНЫ, приняв за её концы пару
годов, — и переспрашивало о том, что названо совершенно однозначно.

Замер после правки на том же наборе: семь вилок из семи прочитаны обоими
концами; на восьми не-вилках (включая две ловушки с годами и две с горизонтом
рядом с величиной) ложных вилок ноль и ложных переспросов ноль.

### 3.13 Эластичность перестала быть литературной константой

Сценарная ветка стояла на числе из литературы. Число разумное, но чужое:
проверить его на наших данных было нечем, а весь сценарный расчёт держался на
нём одном. Теперь оно измеряется — по квартальным рядам добычи, потребления,
запасов и цены, вычитанным из таблиц STEO нашим же трактом чтения PDF.

Внешний источник рядов при этом не понадобился и не подошёл бы:
`api.eia.gov` без ключа отвечает 403. Взять их из корпуса оказалось не обходным
путём, а более правильным устройством — прогноз опирается на данные, прочитанные
той же дугой восприятия, и любое число прослеживается до страницы отчёта.

#### Что вскрыло измерение

**В сценарной формуле стояла не та величина.** Формуле
`P₁/P₀ = (1 + ΔQ/Q₀)^(1/ε)` нужна эластичность РЫНОЧНОГО КЛИРИНГА: на сколько
процентов должна сдвинуться цена, чтобы рынок поглотил сдвиг ПРЕДЛОЖЕНИЯ на
процент. Мы подставляли туда эластичность СПРОСА — сколько потребления уйдёт
при росте цены. Это разные величины, и между ними стоит БУФЕР ЗАПАСОВ: разрыв
закрывается не только сокращением потребления, но и расходом хранилищ, а
хранилища работают как дополнительное предложение и гасят ценовой отклик.

| величина | оценка на корпусе | 95% интервал |
|---|---|---|
| эластичность спроса | −0.11 | −0.20 … −0.02 |
| эластичность клиринга | −0.31 | −0.71 … −0.20 |

Разница втрое. На шоке −2 млн барр./сут расчёт выдавал ×1.219 вместо ×1.066 —
это не уточнение третьего знака, это другой ответ.

#### Как обойдена эндогенность

Цена и потребление определяются одновременно, поэтому простая регрессия
потребления на цену смешала бы движение ВДОЛЬ кривой спроса с её СДВИГАМИ.
Нужен инструмент — величина, которая двигает цену, но сама не сдвигает спрос.
Здесь это изменение мировой добычи: корпус накрывает крупный перебой предложения
(2026Q2, −8.3% за квартал), а перебой добычи к состоянию спроса отношения не
имеет. Инструмент сильный — первая ступень объясняет 72% дисперсии изменения
цены.

Оценка спроса считается методом инструментальных переменных, оценка клиринга —
прямой регрессией отклика цены на сдвиг предложения, то есть измеряется ровно
тот параметр, который потом подставляется в формулу.

#### Третий метод прогноза, выросший из тех же рядов

Те же данные дают прогноз цены ИЗ ФАКТОРОВ:
`Δln P = a + b·Δln S + c·ΔI`, R² = 0.89 на девяти кварталах. Добыча одна
объясняет 72% движения цены, добыча вместе с изменением запасов — 89%. Знак при
запасах положителен, и это содержательно: расход хранилищ снижает цену
относительно того, что дал бы один шок добычи.

В модель подставляются прогнозные значения факторов, которые EIA печатает в тех
же таблицах на шесть кварталов вперёд. Результат печатается рядом с основным
прогнозом как ВТОРОЕ МНЕНИЕ вместе с величиной расхождения: сглаживание и ARIMA
родственники и почти всегда согласны, поэтому их согласие мало что значит, а
согласие с методом, смотрящим на добычу и запасы, значит много. На момент
написания расхождение составляет 44%, и это содержательный факт: рынок и
балансовый прогноз EIA сейчас говорят разное.

#### Полоса считает ДВА источника ошибки

Остаток регрессии отвечает только на вопрос «насколько точно модель переводит
факторы в цену» и молчит о том, что сами факторы взяты из ПРОГНОЗА EIA. Второй
источник измерен на нашем же корпусе — по расхождению между прогнозом добычи на
ближайший квартал и тем, чем этот квартал оказался (у каждого квартала есть
прогнозная версия из раннего выпуска и фактическая из позднего). Он оказался
ВДВОЕ БОЛЬШЕ первого: 0.018 на добыче при коэффициенте −5.9 даёт 0.107 в
логарифме цены против 0.049 у остатка модели. Коридор по одному лишь остатку
рисовал бы уверенность, которой нет.

#### Границы, которые надо назвать вслух

* Наблюдений девять. Интервалы широки, и это видно в самих интервалах.
* Добыча экзогенна не полностью: производители реагируют на цену.
* Длинный конец эластичности НЕ измерен — корпус накрывает полтора года.
  Численно измеренный короткий конец (−0.31) почти совпал с литературным
  длинным (−0.30), а значит на этих данных горизонты не различаются, и
  интерполяция между ними почти плоская. Это честное отражение незнания, а не
  свойство рынка.
* Прогноз факторов взят у EIA: если они ошибутся в добыче, ошибёмся и мы.

### 3.14 Фильтр жёлтой прессы: явные списки доменов

Требование 2.3 просит отфильтровать часть жёлтой прессы. Сделано явными
списками: 16 доменов в отказе, 20 — в предпочтении (отраслевые издания и
агентства).

Список можно прочитать, оспорить и поправить под редакционную политику
заказчика. Суждение модели о «желтизне» источника прочитать нельзя, оспорить
нечем, и оно меняется от запуска к запуску. Для регулируемой отрасли первое
свойство важнее любого выигрыша в гибкости.

### 3.15 Память диалога: три хранилища, жёсткий бюджет, без пересказа

Уточняющий вопрос — обычная форма работы аналитика: «спрогнозируй Brent на три
месяца», затем «а если ОПЕК+ сократит на 2 млн?», затем «а на пять лет?». Без
памяти второй и третий вопросы бессмысленны: в них нет ни инструмента, ни
горизонта, ни даже слова «нефть».

Ходы разговора хранит checkpointer LangGraph, разговор называется `thread_id`
(в интерфейсе он живёт в сессии браузера, поэтому два окна — два разных
разговора). Хранилище выбирается настройкой `CONVERSATION_MEMORY`:

| режим | где живёт разговор | когда нужен |
|---|---|---|
| `sqlite` (умолчание) | в файле `CHECKPOINT_DB` | разговор переживает перезапуск |
| `memory` | в оперативной памяти процесса | ничего не пишется на диск |
| `off` | нигде | каждый вопрос с чистого листа |

★Настройка решает ОДИН вопрос: попадает ли переписка с аналитиком на диск. Это
данные заказчика, и решение принимает тот, кто разворачивает систему, а не тот,
кто писал код. Опечатка в значении — ошибка, а не тихий откат к умолчанию: иначе
система выглядела бы исправной, просто «потерявшей память».

⚠Умолчание изменено с `memory` на `sqlite` вместе с появлением списка разговоров
и поиска по ним: с `memory` половина кнопок интерфейса выключена, то есть прежнее
умолчание отдавало бы урезанный продукт. Реестр и история поиска включены ровно
при `sqlite`, а при остальных значениях интерфейс говорит, что их нет и почему, —
обойти настройку молча они не могут по устройству.

### 3.15б Подключение разговоров источниками: почему ссылки, почему без надбавки
### и почему возможность ВЫКЛЮЧЕНА

Замысел прост: разговор, в котором уже разобрана тема, можно подключить к
новому — и найденные там фрагменты отчётов станут кандидатами при поиске.

**Почему едут ссылки, а не текст.** Из подключённого разговора переносятся
только идентификаторы фрагментов и ни одного утверждения модели. Причина не в
экономии места. Перенеси мы формулировку прошлого ответа — и модель получила бы
в качестве источника собственный прошлый вывод, а он в ответе выглядел бы как
проверяемая цитата из отчёта. Это круговая ссылка: утверждение подтверждает само
себя, а читатель видит ссылку на страницу. Гарантия сделана структурной, а не
дисциплинарной: в таблице следа есть колонки под идентификатор, позицию и ход —
и ни одной под текст, поэтому перенести формулировку попросту некуда. Побочная
выгода: идентификатор выведен из содержания фрагмента, поэтому ссылка сама
ломается, когда фрагмент изменился при пересборке индекса, — и это правильно,
изменившийся фрагмент уже не тот, на который ссылались.

**Почему подключённым фрагментам не даётся надбавки.** Они соревнуются с
обычными кандидатами по той же мере (косинус между вопросом и вектором
фрагмента) и с тем же порогом. Любая надбавка «за подключённость» была бы
выбранным числом, а не выведенным: её вклад в выдачу остался бы неизвестным, и
отличить «подключение помогает» от «подключение всё перемешивает» стало бы
нечем. Надбавка вдобавок легко возникает НЕЗАМЕТНО — что и случилось: в первой
версии слияния заимствованный фрагмент вытеснял последнего в списке, а порядок
обычных находок задан слиянием двух ветвей поиска, а не оценкой. В итоге
фрагмент с оценкой 0.6592 вытеснил фрагмент с 0.6842 — то есть выиграл позицией
вместо меры. Поймал это отрицательный контроль; теперь вытесняется слабейший по
оценке, и вход разрешён только тому, кто его превосходит.

**Почему возможность выключена (`LINK_THREADS=false`).** Мера была объявлена до
кода и состоит из двух половин.

| половина меры | требование | измерено |
|---|---|---|
| польза | нужный фрагмент входит в top-5 | **2 из 3** переформулировок |
| вред (отрицательный контроль) | на посторонних вопросах выдача не меняется | **1 из 6**, то есть 17% |

Польза есть, вред больше объявленного «около нуля». Незамеренная возможность в
поставке хуже отсутствующей: она выглядит работающей. Поэтому код на месте и
покрыт тестами, а умолчание — «выключено», и включает его тот, кто согласен с
названной ценой.

⚠Отдельно стои́т сказать, что показал разбор изменившихся случаев: вытесняются
почти всегда строки-пустышки вида `United States ................` с оценкой
0.62–0.65, а входят строки с настоящим содержанием (`U.S. total crude oil
production`, 0.69–0.71). То есть 17% — это в основном перетасовка почти
одинаковых по оценке фрагментов в области, где сам поиск работает слабо. Это
довод не за включение, а за отдельную работу над качеством выдачи.

### 3.15а Поиск по разговорам: почему `trigram`, а не поиск по словоформам

Полнотекстовый поиск SQLite (FTS5) штатно режет текст на слова и сопоставляет их
целиком. Русской морфологии в нём нет: запрос «добыча» не нашёл бы «добычи», и
поиск по собственной переписке проваливался бы на каждом втором слове — а
пользователь в этот момент читает ответ «ничего не найдено» и делает вывод, что
такого разговора не было.

Взят токенизатор `trigram`: он режет текст на тройки символов, то есть ищет
подстроку и от морфологии не зависит. Цена названа заранее и уплачена сознательно:
индекс больше, а короткие запросы дают ложные срабатывания — отсюда минимальная
длина запроса в три буквы, названная в самом интерфейсе.

★Одного токенизатора оказалось мало, и это выяснилось замером до написания кода.
Триграммы ищут ПОДСТРОКУ: «добыч» действительно находит «добычи», но «добыча» не
находит ничего, потому что одна форма не входит в другую. Проверка на живом
индексе: «добыча» — 0 совпадений, «сокращение» — 0, «прогнозы» — 0. Поэтому у
слов запроса срезается хвост (от восьми букв минус три, от шести минус две, от
четырёх минус одна). После этого шесть словоформ из шести нашли свои пары, а
четыре посторонних слова по-прежнему не нашли ничего — вторая половина обязательна,
иначе мера «поиск находит всё» неотличима от «поиск находит что попало».

Полноценный стеммер русского языка взял бы и спряжение, но это отдельная
зависимость ради одного поля. Граница приёма поэтому названа прямо: склонение
берётся, спряжение — нет («снижаться» не найдёт «снижается»), и на это стои́т
отдельный тест, который упадёт, если морфология когда-нибудь появится.

**Бюджет истории — жёсткое число знаков, старые ходы отбрасываются целиком.**
Пересказ старых ходов моделью означал бы ещё один вызов на каждом шаге:
задержку, деньги и недетерминизм там, где его быть не должно — два одинаковых
разговора обязаны давать одинаковый промпт. Отбрасывается голова, а не хвост:
свежие ходы нужнее для разрешения «а на пять лет?».

★Подрезка идёт ПРИ ЗАПИСИ, а не только при сборке промпта, и это не деталь.
Пока она стояла лишь в сборке, первый же настоящий ответ (три-пять тысяч знаков)
выбирал весь бюджет, и история схлопывалась до единственного последнего хода:
снаружи память выглядела работающей, а не помнила ничего. Поймано на первом
сквозном прогоне и закрыто тестом.

★**Бюджеты заданы в ЗНАКАХ, а окно модели меряется в ТОКЕНАХ — и разрыв между
ними измерен.** На нашем материале отношение вышло 2.48 знака на токен по
английским таблицам STEO и 2.02 по русским ответам системы (замер токенизатором
`cl100k_base`; подключённая модель может быть другой, поэтому это оценка
порядка, а не точное число). Сумма бюджетов по умолчанию — 15 000 знаков, то
есть примерно 6000–7400 токенов ТОЛЬКО контекста, без задания и без ответа. При
окне 8k этого впритык, и узнаётся такое отказом сервера посреди работы. Поэтому
окно можно назвать настройкой `LLM_CONTEXT_TOKENS`, и тогда несоответствие
выясняется при старте. ★Именно предупреждение, а не отказ: перевод знаков в
токены оценочный, и ронять запуск на чужом токенизаторе значило бы поменять один
тихий отказ на другой — громкий и часто ложный.

**История — контекст вопроса, а НЕ источник.** В промпте она стоит до
источников и помечена прямо: ссылаться на неё нельзя, каждое число обязано нести
ссылку на отчёт, веб или расчёт, даже если то же число уже звучало в разговоре.
Иначе модель процитирует собственный прошлый ответ как проверяемый источник —
то есть выдаст пересказ за факт.

**Горизонт наследуется, величина шока — нет.** После «спрогнозируй на 3 месяца»
вопрос «а если сократят на 2 млн?» считается на те же 90 дней. А вот наследуемый
сценарий стал бы липким: однажды названное «при сокращении на 1.5» тихо красило
бы все последующие ответы, и вернуться к базовому прогнозу можно было бы только
начав разговор заново. Горизонт нейтрален и нужен всегда; допущение о шоке должно
быть названо.

#### Что нашёл сквозной прогон, чего не нашли тесты

Четыре дефекта, каждый из которых виден только из ответа целиком:

1. **Знак сценария.** Список корней «сокращ, снижен, уменьш, срез» не содержал
   корня «сократ», и вопрос «а если ОПЕК+ СОКРАТИТ добычу на 2 млн барр./сут?»
   считался как сценарий УВЕЛИЧЕНИЯ: система отвечала падением цены на вопрос о
   её росте. ★Ошибка знака дороже ошибки величины: диапазон читатель
   перепроверит, направление примет на веру. Заметила это сама модель — она
   написала в ответе, что расчёт противоречит вопросу.
2. **Числительные словом.** В продолжении разговора человек почти не пишет
   цифру, а парсер знал только `\d+`: «а на пять лет?» молча считалось на
   прежние 90 дней.
3. **Молчаливый потолок горизонта.** Прогноз ограничен 730 днями — дальше
   истории это арифметика, а не анализ. Но ограничение применялось молча:
   спросив пять лет и увидев «горизонт 730 дн.», человек читает это как ответ
   на свой вопрос и ошибается в 2.5 раза. Теперь урезание объявляется в тексте
   расчёта.
4. **Множитель сценария применялся дважды — в тексте ответа, не в расчёте.**
   Расчётный блок печатал уже сдвинутые числа («прогноз 97.21») и ниже строку
   «сценарий … ⇒ цена ×1.049», не сказав, что множитель уже применён. Модель
   прочитала его как ещё не применённый, умножила второй раз и выдала 101.98
   вместе с так же раздутыми границами интервала. ★Расчёт был верен; ошиблась
   ПОДАЧА: величина и результат её применения стояли рядом без указания
   порядка, а такой текст неотличим от инструкции «умножь». Теперь порядок
   назван словами, базовая цифра печатается рядом, и пометка «множитель уже
   учтён» стоит у самой строки прогноза, а не абзацем ниже.

### 3.16 Выбор компонентов — по критерию «проверяется без регистрации»

| Компонент | Выбор | Почему |
|---|---|---|
| Эмбеддинги | fastembed / ONNX, многоязычная модель | Корпус заказчика не покидает машину; без torch образ легче примерно на 2 ГБ. Многоязычность обязательна: отчёты английские, вопросы русские |
| Векторная БД | Qdrant, встроенный режим | Из списка ТЗ; пишет в каталог, отдельный сервис поднимать не нужно — отсюда запуск одной командой |
| Веб-поиск | Библиотека `ddgs`, сервис задан явно (`WEB_BACKEND=brave`) | Единственный из списка ТЗ без API-ключа: проверяющий клонирует репозиторий и видит работу, не регистрируясь. Сервис назван поимённо — см. 3.16 |
| Цены | yfinance (`BZ=F`) | Назван в ТЗ, не требует ключа |
| Корпус | EIA STEO, 8 выпусков | Из трёх названных агентств только EIA отдаёт PDF напрямую — см. ограничения |
| LLM | любой OpenAI-совместимый endpoint | Умолчание локальное, поэтому система работает без ключей; заказчик подставляет свой |

Сквозной критерий: рецензент должен увидеть работающую систему, не заводя ни
одной учётной записи. Каждый обязательный ключ — это шанс, что вместо продукта
проверяющий увидит форму регистрации.

### 3.16а Веб-поиск: адресат вопроса назван поимённо

Когда включён веб-поиск, наружу уходит текст вопроса пользователя. Значит,
вопрос «куда именно» — не деталь реализации, а часть обещания о локальности.

**Что обнаружилось.** Библиотека `ddgs` (9.15.0) названа в честь DuckDuckGo,
но им не ограничивается: в режиме по умолчанию (`auto`) она обходит семь
сервисов — Wikipedia, Grokipedia, DuckDuckGo, Yahoo, Mojeek, Brave, Startpage —
и выбирает адресата в момент запроса. В контрольном прогоне вопрос ушёл на
Mojeek. Назвать адресата заранее в этом режиме нельзя в принципе, то есть
строка «веб-поиск через DuckDuckGo» в документации была неверной.

**Что сделано.** Сервис задаётся одним значением (`WEB_BACKEND`, умолчание
`brave`) и проверяется до запроса. Режим `auto`, значение `all` и список из
нескольких имён отвергаются: при них поиск не выполняется вовсе и сообщает
причину. Отдельно отвергается неизвестное имя — сама библиотека на него
реагирует не отказом, а **молчаливым возвратом к `auto`**, поэтому опечатка в
настройке выглядела бы как работающий поиск и рассылала бы вопрос по семи
сервисам.

**Почему Brave — замером.** Три вопроса отраслевого рода, каждый сервис
опрошен отдельно, три прогона:

| сервис | результатов (1/2/3) | авторитетных | прогонов без отказа |
|---|---|---|---|
| `brave` | 45 / 45 / 45 | 21 / 21 / 21 | 3 из 3 |
| `yahoo` | 14 / 7 / 14 | 5 / 3 / 4 | 0 из 3 |
| `duckduckgo` | 0 / 0 / 30 | 0 / 0 / 6 | 1 из 3 |
| `mojeek` | 0 / 0 / 0 | 0 / 0 / 0 | 0 из 3 |
| `startpage` | 0 / 0 / 0 | 0 / 0 / 0 | 0 из 3 |

Решило не число результатов, а повторяемость. Замер опроверг ожидание: я
предполагал, что ответят DuckDuckGo, Yahoo и Mojeek, а Brave и Startpage
откажут, — не угадал ни в одну сторону. Воспроизводится скриптом
`scripts/probe_web_backends.py`.

**Как это проверено — не чтением кода.** Запрос пропущен через посторонний
прокси-свидетель, записывающий имя хоста, о котором просит клиент. Обычный
прогон: ровно одно обращение, `CONNECT search.brave.com`, к остальным шести —
ни одного. Отрицательный контроль (свидетель отказывает именно Brave):
`failed: brave: ConnectError…`, ноль результатов и ни одной попытки уйти к
соседу. Отказ выглядит отказом, а не тихой заменой адресата.

Сторож в `tests/test_web_backend.py` роняет сборку при возврате к `auto` или к
списку сервисов: такой откат не ломает ничего другого и в интерфейсе не виден.

### 3.17 Роль и тон принадлежат заказчику, правила при отсутствии данных — нет

Область экспертизы, требования к стилю и реплика на вопрос вне компетенции —
предмет редакционной политики: что именно считать своей темой и каким тоном
разговаривать, решает тот, чьё имя стоит на продукте. Поэтому оба текста
задаются файлами (`SYSTEM_PROMPT_FILE`, `OUT_OF_SCOPE_FILE`), и менять их можно
не трогая код. Пустое значение означает «взять наш текст», так что система
пригодна из коробки.

Правила при отсутствии данных вынесены не были, и это главное решение здесь. На
них — «никогда не выдумывай числа», «нет ответа в источниках — скажи прямо»,
приоритет источников — стои́т сверка цитат и весь раздел о проверяемости. Это не
пожелание к тону, а продаваемое свойство.

**Защита сделана устройством, а не проверкой текста.** Обязательный блок
дописывается кодом к любому тексту роли, и удалить его из файла нельзя, потому
что его в файле нет. Очевидная альтернатива — проверять, что нужные фразы
присутствуют в файле заказчика, — слабее вдвойне: она ловит удаление правила и
не ловит его переписывание в противоположное («если источника нет, оцени
приблизительно»), а заодно запрещает заказчику переформулировать ровно то, что
он вправе переформулировать.

**Негодный файл останавливает запуск, а не заменяется умолчанием молча.**
Заказчик, указавший путь с опечаткой, иначе получил бы работающую систему с
нашим тоном вместо своего и не узнал бы об этом никогда. Проверяются пять
случаев: пути нет, по пути каталог, файл пуст, в файле одни пробелы, текст
длиннее 10 000 знаков. Последний порог — не аккуратность, а бюджет контекста:
роль едет в каждый запрос к модели и вытесняет из окна сами отчёты. Взят с
десятикратным запасом к нашим текстам (роль и стиль — 1014 знаков, реплика
отказа — 394).

Замер: пять видов негодного файла из пяти отвергнуты с названной причиной;
законный файл принят, и его текст доходит до промпта, вытесняя наш; обязательные
правила при этом остаются на месте — проверено файлом роли, в котором их нет
вовсе.

## 4. Проверяемость как предмет поставки

Продукт обещает проверяемые ссылки. Объявить это мало: непроверенное обещание
стоит для рецензента ровно столько же, сколько его отсутствие.

`scripts/check_citations.py` берёт каждый абзац ответа и сверяет названные в нём
числа с источником, на который абзац ссылается.

**Числа берутся заново из PDF.** Выдача поиска для сверки не годится: она
подтвердила бы согласие модели с поиском и промолчала бы о том, что оба
ошиблись вместе. Проверка не должна делить механизм с проверяемым.

Три условия, без которых инструмент врал бы в тихую сторону:

1. **Ссылка закрывает то, что перед ней.** Итоговый абзац законно смешивает
   источники: предложение про EIA закрыто ссылкой на отчёт, следующее про ОПЕК
   — ссылкой на веб. Сверка абзаца целиком гнала бы все его числа по страницам
   отчётов и объявляла бы веб-числа неподтверждёнными.
   ★Ссылки, идущие ПОДРЯД, при этом считаются одной группой, и числа перед ними
   сверяются с объединением их страниц. Фраза «в мае и июне прогноз подскочил до
   109.73 и 109.78 соответственно [май, с. 36], [июнь, с. 34]» ставит оба числа
   перед первой ссылкой; разрез строго по ней требовал бы найти оба на майской
   странице и объявлял бы июньское выдуманным. Различить по тексту, какое число
   к какой ссылке относится, нельзя в принципе. Группируются только однородные
   ссылки: если склеивать «[Отчёт …], [Источник …]», не найденное в отчёте число
   списывалось бы на непроверяемый веб, то есть перечисление источников стало бы
   способом уйти от проверки.
2. **Числа с запятой равноправны числам с точкой.** Отчёты английские и пишут
   `1.3`, ответы русские и пишут `1,3`. Шаблон, знающий только точку, не видит
   половину написаний — и печатает «не подтверждено: 0» ровно тем же тоном, что
   и полная проверка.
3. **Состояний три.** «Нечего проверять» обязано отличаться от
   «проверено и чисто»: ответ без единого числа и ответ, все числа которого
   подтверждены, в двузначной шкале выглядят одинаково. Отдельно учитываются
   числа из веба — они непроверяемы по природе, поскольку страница живёт в сети
   и меняется; считать их сверенными неправда, считать неподтверждёнными —
   клевета.

Числа прогноза проверяются тоже. В корпусе отчётов их нет по природе, но
перенос числа из расчётного модуля в текст ответа проверить можно. Именно на
этом шаге модель и ошибается: считает модуль, а переписывает число она.

Результат на демонстрационных сценариях:

```
сценарий                              сверено  не подтв.  без ссылки   веб
01 Ответ на основе отчёта                  27          0           0     0
02 Ответ на основе веб-поиска               0          0           0     0
03 Комбинированный ответ                    6          0           0     4
04 Вызов расчётного модуля                 28          0           0     0
05 Запрос вне компетенции                   0          0           0     0
```

61 число сверено, ни одного неподтверждённого, ни одного без ссылки.

**Приёмка инструмента двусторонняя.** Проверка, которая никогда не говорит
«нет», неотличима от отсутствующей, поэтому она прогоняется на подложных
ответах: ложное число из отчёта, ложное число из расчёта, абзац с числом без
всякой ссылки. Все три случая ловятся. Отдельным кодом возврата отмечено «не
отработала» — например, если в ответах не нашлось ни одного числа со ссылкой.

Кроме того, разметка колонок проверена вручную по источнику: шапка таблицы
`Q1 Q2 Q3 Q4 | Q1 Q2 Q3 Q4 | Q1 Q2 Q3 Q4 | 2025 2026 2027`, строка США
`13.28 13.51 13.78 13.77 | 13.57 13.88 13.78 13.88 | 13.99 14.07 14.00 14.07` —
модель разложила значения по годам и кварталам верно.

**Сверка входит в автоматическую приёмку, а не запускается по памяти.** Прогон
руками и проверка, которой нет, различаются только дисциплиной запускающего:
пустой результат в обоих случаях выглядит одинаково зелёным. Поэтому сверка
цитат стои́т отдельным тестом: шесть диверсий на подложном корпусе из двух
страниц идут всегда, а прогон по настоящим отчётам и настоящим демо-ответам
добавляется сверху, когда корпус есть на машине.

**Настройки проверяются при старте.** Опечатка в `.env` обычно не ломает
систему, а тихо меняет её поведение: `ELASTICITY_SOURCE=mesured` переключал
расчёт с эластичности, измеренной на корпусе, на литературную — то есть менял
числа в ответе и молчал об этом. Теперь каждое значение сверяется с реестром
допустимого до первого вопроса; отказ называет имя переменной, полученное
значение и допустимое, и перечисляет все находки разом. Реестр накрывает все 33
поля конфигурации: у 24 есть границы или замкнутое множество значений, а
оставшиеся 9 (имя модели, пути, ключ) объявлены свободными С ПРИЧИНОЙ — иначе
«проверять нечего» и «проверить забыли» выглядели бы в коде одинаково.

**Гигиена состояния разговора проверяется тоже.** Поле, которое пишется не на
всякой ветке графа, а читается всегда, без явного сброса живёт в хранилище
разговора вечно: отказ веба, случившийся на одном вопросе, приезжал оговоркой в
ответ на следующий, который в веб не ходил. Правило «такие поля пишутся каждый
ход» было записано словами рядом с кодом и не сработало трижды подряд — каждый
раз на новом поле. Теперь поля состояния разделены на три класса (сбрасываемые
каждый ход, приходящие со входом, живущие дольше хода по замыслу), сброс идёт по
перечню, а тест требует, чтобы деление накрывало состояние целиком: поле, не
отнесённое ни к одному классу, красит приёмку сразу, а не через два хода
разговора у пользователя.

Модульных тестов — 576. ★Это число намеренно названо ЗДЕСЬ И БОЛЬШЕ НИГДЕ: оно
устаревает при каждой правке, а утверждение, живущее в нескольких копиях,
расходится молча — в этом самом документе оно успело простоять как «87» после
того, как тестов стало впятеро больше.

## 5. Защита контейнера

Этого раздела в задании нет. Мы считаем его обязательным: решение
разворачивается в контуре банка, работает с непубличными аналитическими
материалами и ходит в интернет. Система, которая всё это делает, обязана иметь
осознанный периметр независимо от того, спросили о нём или нет.

Каждая угроза разобрана отдельным блоком, и в каждом разделено: что сделано в
поставке, что задаётся командой запуска, что остаётся рекомендацией к
развёртыванию. Смешивать эти три вещи нельзя: намерение, выданное за меру, —
худший вид отчёта о безопасности.

**Шесть мер переведены из второй категории в первую.** Раньше неизменяемая
корневая ФС, временный каталог в памяти, снятые возможности ядра, запрет
повышения привилегий и потолки памяти и процессора задавались длинной командой
запуска — то есть действовали ровно настолько, насколько развёртывающий её не
забыл. Теперь они лежат в `compose.yaml`, версионируются вместе с кодом и
применяются сами: `docker compose up`. Чтобы их снять, нужно действие — правка
файла, видимая в истории, — а не забывчивость. Мера, применяемая по памяти, и
мера, применяемая по умолчанию, — разные меры, как бы одинаково они ни
выглядели в документе.

Применённость проверяется не на слово:

```bash
docker compose exec analyst sh scripts/check_hardening.sh
```

Шесть строк и код возврата. **Каждая проверка различает режимы запуска, и это
замерено, а не заявлено:** контейнер запущен дважды, без флагов и с ними. Без
них — ноль мер из шести и код 1; с ними — шесть из шести и код 0; через
`docker compose up`, без единого флага руками, — тоже шесть из шести.

Требование «различать режимы» здесь не формальность. В прошлый раз (5.3) две из
трёх напечатанных проверок отвечали одинаково с флагами и без них, потому что и
пустой набор эффективных возможностей, и отказ записи в системный каталог даёт
сам непривилегированный пользователь. Поэтому в скрипте проверяется
ограничивающий набор `CapBnd`, а не эффективный; запись в `/app`, куда
пользователь писать вправе, а не в `/etc`; тип файловой системы на `/tmp`, а не
просто возможность записи туда.

Общий принцип, которому подчинены все решения ниже: **запрещено всё, что не
разрешено явно**. Разрешения перечислимы и коротки, и потому их можно
предъявить.

### 5.1 Утечка корпуса заказчика во внешние сервисы

**Периметр.** Отраслевая аналитика, внутренние оценки, непубличные отчёты. При
обычной сборке RAG текст каждого фрагмента уходит в API эмбеддингов, то есть
весь корпус целиком покидает контур штатным режимом работы. Происходит это тихо
и не выглядит инцидентом.

**Что сделано.** Эмбеддинги считаются локально через fastembed/ONNX; наружу не
уходит ни один фрагмент. Корпус и индекс монтируются томом и не запекаются в
образ, поэтому не попадают в артефакт сборки, который потом расходится по
реестрам. `data/` исключён из контекста сборки в `.dockerignore` — демон его
даже не видит.

**Альтернативы.** API эмбеддингов OpenAI или Cohere: качество кросс-языкового
поиска выше, работы меньше, зависимость от ключа. Запекание корпуса в образ:
воспроизводимость поставки лучше, но образ становится носителем данных
заказчика.

**Почему так.** Для регулируемой отрасли граница «данные не покидают контур»
дороже нескольких процентов качества поиска. Это решение и определило выбор
модели эмбеддингов: она обязана быть многоязычной, потому что заменить её на
сильную одноязычную с переводом через внешний сервис — значит вернуть ту же
утечку с другой стороны.

### 5.2 Секреты в артефактах сборки и в истории репозитория

**Периметр.** Ключ LLM-провайдера, токены поисковых API. Попав в слой образа
или в коммит, секрет остаётся там навсегда: история неизменяема, а удаление
файла следующим коммитом ничего не удаляет.

**Что сделано.** Все ключи — только через переменные окружения; `.env` в
`.gitignore` и в `.dockerignore`, в репозитории лежит лишь `.env.example`.
Проверено: `git ls-files .env` не возвращает ничего.

**Альтернативы.** `ARG`/`--build-arg` — попадают в историю слоёв и видны в
`docker history`. Секрет файлом в образе — то же самое, только нагляднее.
BuildKit `--mount=type=secret` и Docker/Kubernetes secrets — правильный
промышленный путь.

**Почему так.** Переменные окружения — минимум, который работает везде и не
требует от проверяющего инфраструктуры. При развёртывании в контуре банка
рекомендуем перейти на секреты оркестратора: переменные окружения видны в
`docker inspect`, в списке процессов и — это третье место мы нашли, добавляя
`compose.yaml`, — в выводе `docker compose config`, который печатает содержимое
`.env` открытым текстом. Последнее обманчивее прочих: команда выглядит как показ
конфигурации, а не как показ секретов, и её выхлоп естественно попадает в
переписку и в тикеты. Слабость эта известная, и мы называем её сами.

### 5.3 Компрометация процесса приложения и привилегии на хосте

**Периметр.** Streamlit, LangGraph, парсер PDF, ONNX-рантайм, два десятка
транзитивных зависимостей. Любая брешь в этой цепочке даёт выполнение кода
внутри контейнера. Дальше вопрос один: чем именно он ограничен.

**Что сделано.** Образ создаёт непривилегированного пользователя (`uid 1000`) и
переключается на него: `USER analyst`. Без этого контейнер работал бы от root,
и от хоста его отделяло бы только ядро.

**Что в поставке (было — командой запуска).** Все флаги ниже лежат в
`compose.yaml` и применяются сами:

```bash
cp .env.example .env
docker compose up
```

Развёрнутая форма приведена дальше не как рекомендация к набору руками, а
затем, что каждый флаг здесь объяснён поимённо, и объяснение должно стоять
рядом с ним:

```bash
docker run -p 127.0.0.1:8501:8501 \
  --read-only --tmpfs /tmp \
  --cap-drop=ALL --security-opt no-new-privileges \
  --memory 6g --cpus 4 \
  --user "$(id -u):$(id -g)" \
  -v "$PWD/data:/app/data" --env-file .env \
  neftegaz-analyst
```

Первая строка не декоративна: `.env` в репозиторий не входит, и на свежем
чекауте `--env-file` останавливает запуск ещё до старта контейнера.

Вторая оговорка касается адреса модели. Умолчание `OPENAI_BASE_URL` указывает
на `127.0.0.1`. Для запуска из виртуального окружения это верно. Внутри
контейнера `127.0.0.1` — его собственный петлевой интерфейс, и модели там нет.

Из контейнера работают три формы. Первая — адрес хоста в сети докера
`http://172.17.0.1:PORT/v1`; модель тогда обязана слушать этот адрес, одного
петлевого ей мало. Вторая — внешний endpoint вроде GigaChat. Третья — запуск с
`--network host`, где `127.0.0.1` означает то же, что на хосте. Третья форма
удобна для демонстрации, но отменяет публикацию портов, поэтому адрес
прослушивания задаётся переменной `STREAMLIT_SERVER_ADDRESS=127.0.0.1`.

`--cap-drop=ALL` снимает все возможности ядра; `no-new-privileges` запрещает
повышение через suid; `--read-only` делает корневую файловую систему
неизменяемой, оставляя запись только в смонтированный `data` и в `tmpfs`.

Снятие возможностей проверяется по ограничивающему набору `CapBnd`:
эффективный `CapEff` у непривилегированного пользователя пуст и без этого флага.

**Альтернативы.** Оставить root — принято по умолчанию и работает без оговорок
с правами на смонтированный том. Rootless podman — снимает демон, работающий от
root, то есть убирает целый класс путей эскалации. gVisor или Kata Containers —
перехват системных вызовов или отдельное ядро, заметная цена по
производительности. Полная виртуальная машина — максимальная изоляция,
максимальная цена.

**Почему так.** Выбран баланс «непривилегированный пользователь плюс снятые
возможности плюс неизменяемая ФС»: он ничего не стоит по производительности, не
требует особой инфраструктуры и убирает самые дешёвые для атакующего пути. У
него есть цена, и мы её называем: `--user` в команде выше не украшение. Образ
работает от `uid 1000`, а смонтированный каталог принадлежит запускающему, и
без совпадения владельца Qdrant не откроет свой файл блокировки. Это выяснилось
прогоном: контейнер поднимался и переходил в `healthy`,
после чего падал на первом же запросе.
gVisor и Kata не взяты потому, что их выигрыш относится к сценарию «в
контейнере исполняется недоверенный код». У нас в контейнере исполняется наш
код, а недоверенными оказываются данные, которые он читает (см. 5.5).

### 5.4 Неограниченный исходящий трафик

**Периметр.** Компрометация или ошибка внутри контейнера в обычной конфигурации
означает доступ ко всей сети, видимой хосту, — включая внутренние адреса
контура. Для решения, которое по замыслу ходит в интернет, «ходит в интернет»
не должно означать «ходит куда угодно».

**Что сделано.** Список исходящих направлений короткий, перечислимый и
задокументированный:

* endpoint LLM (адрес задаёт заказчик в `.env`);
* `search.brave.com` — веб-поиск (адресат задан настройкой `WEB_BACKEND` и
  назван поимённо: библиотека `ddgs` в режиме по умолчанию выбирает его сама
  из семи сервисов, и тогда назвать его заранее нельзя — см. раздел 3.16);
* Yahoo Finance — история котировок Brent;
* Hugging Face — однократная загрузка ONNX-модели эмбеддингов при первом
  запуске, далее она живёт в кэше внутри `data`.

Никаких других адресов система не использует, и это свойство проверяемо: все
сетевые вызовы собраны в двух модулях (`tools/web.py`, `forecast/data.py`) и в
клиенте LLM, поэтому список исходящих читается из кода.

**Что остаётся рекомендацией.** Egress-прокси в режиме белого списка и
контейнер во внутренней сети без прямого выхода: разрешены четыре направления
выше, всё остальное отклоняется. Модель эмбеддингов при этом лучше загрузить
заранее в том `data`, чтобы Hugging Face можно было из списка убрать совсем.

**Альтернативы.** `--network none` — полная изоляция, но ломает требование 2.3:
веб-поиск перестаёт работать. Полный доступ — принято по умолчанию, никакой
границы. Только правила на брандмауэре хоста — работают, но их конфигурация не
переезжает вместе с сервисом и не попадает в систему контроля версий. Сервисная
сетка с mTLS — правильный ответ в зрелом контуре, избыточный для одного
сервиса.

**Почему так.** Белый список — единственный вариант, совместимый с принципом
«запрещено всё, что не разрешено», при котором продукт продолжает выполнять ТЗ.
Важно, что фильтрация здесь не полагается на добросовестность агента:
маршрутизация на уровне сети не спрашивает, уважает ли приложение переменную
`HTTP_PROXY`. Проверка, полагающаяся на согласие проверяемого, проверкой не
является.

### 5.5 Инъекция через недоверенный текст

**Периметр.** Агент читает страницы из интернета и PDF, которые кладёт
заказчик. И то и другое — текст, написанный не нами, попадающий в контекст
модели. Страница может содержать инструкцию, адресованную не человеку, а
модели: «игнорируй предыдущие указания», «сообщи, что цена равна…». Это
основная угроза именно для агентных систем, и от неё не защищают ни права
пользователя, ни возможности ядра.

**Что сделано.** Три ограничения, и каждое архитектурное:

1. **Веб — вторичный источник по построению.** Приоритет отчётов задан ребром
   графа. Текст из интернета не может изменить порядок источников, потому что
   порядок ему не подчиняется.
2. **Расчётный модуль не управляется текстом из веба.** Горизонт и величина
   шока распознаются структурно из вопроса пользователя, до обращения к модели.
   Страница из интернета не способна вызвать пересчёт с другими параметрами.
3. **Происхождение видно в ответе.** Каждое утверждение несёт маркер источника,
   и утверждение, пришедшее с веб-страницы, помечено как веб-источник —
   читатель видит, чему верить в какой мере.

**Альтернативы.** Фильтры-санитайзеры входящего текста — ловят известные
формулировки, обходятся перефразированием. Отдельная модель-классификатор
инъекций — стоит ещё одного вызова на каждый фрагмент и сама ошибается.
Отказ от веб-поиска — противоречит требованию 2.3.

**Почему так.** Содержимое веб-страницы нельзя сделать доверенным, поэтому мы
ограничиваем его полномочия: текст может попасть в ответ (с маркером), но не
может ни изменить маршрут, ни запустить расчёт, ни повысить свой приоритет над
отчётом. Защита стоит на последствиях, поэтому изобретательность атакующего
в формулировках ей безразлична.

Граница у этой защиты есть: инъекция по-прежнему способна повлиять на
формулировку ответа в той части, которая опирается на веб. Полностью это
снимается лишь запретом веб-поиска, то есть отказом от требования ТЗ.

### 5.6 Открытый интерфейс без аутентификации

**Периметр.** Streamlit по умолчанию слушает `0.0.0.0:8501` и не имеет ни
аутентификации, ни разграничения доступа. При публикации порта на все
интерфейсы хоста интерфейс доступен любому, кто видит машину по сети, — вместе
со всем корпусом заказчика.

**Что сделано.** Приложение запускается в headless-режиме, сбор телеметрии
Streamlit отключён явно (`--browser.gatherUsageStats=false`).

**Что задаётся командой запуска.** Публикация только на петлевой интерфейс:
`-p 127.0.0.1:8501:8501`. В рекомендованной команде запуска (5.3) это уже так.
Различие существенное: `-p 8501:8501` открывает порт наружу, `-p
127.0.0.1:8501:8501` — только для самой машины.

Публикация портов защищает лишь до тех пор, пока она вообще применяется. При
`--network host` её нет, и приложение оказывается на всех интерфейсах хоста
само по себе. Поэтому адрес прослушивания вынесен в переменную окружения
`STREAMLIT_SERVER_ADDRESS` вместо флага в `CMD`: флаг командной строки старше
переменной, и попытка сузить адрес переменной молча не сработала бы. Проверка
двусторонняя: с петлевого интерфейса страница отвечает, с адреса хоста в
локальной сети — нет.

**Альтернативы.** Встроить аутентификацию в приложение — быстро делается,
плохо живёт: своя реализация входа в банковском контуре не пройдёт ревизию.
Обратный прокси с корпоративным SSO — правильный путь. Сетевая изоляция без
аутентификации вовсе — приемлемо только для стенда.

**Почему так.** Аутентификация в таком контуре обязана быть корпоративной:
интеграция с SSO — это инфраструктура и политика заказчика. Наша задача —
закрыть порт по умолчанию и явно назвать место стыка, оставив саму
аутентификацию тому, кто ею владеет.

### 5.7 Цепочка поставки зависимостей

**Периметр.** Два десятка прямых зависимостей и существенно больше
транзитивных, устанавливаемых с публичного индекса при каждой сборке.
Скомпрометированная версия пакета получает выполнение кода в контуре.

**Что сделано.** Версии зафиксированы по нижней границе, и рядом с каждой
указано, на какой версии проверялось. Базовый образ — официальный
`python:3.11-slim`.

**Альтернативы.** Точное закрепление (`==`) — воспроизводимость сборки выше,
ломается на другой платформе и консервирует известные уязвимости до ручного
обновления. Закрепление по хешам (`--require-hashes`) — сильнейшая из дешёвых
мер против подмены пакета. Приватное зеркало индекса — промышленный ответ.
Закрепление базового образа по digest вместо тега — защищает от подмены тега.

**Почему так.** Здесь мы сознательно выбрали удобство проверяющего в ущерб
строгости, и не хотим это заминать. Нижняя граница даёт рецензенту собрать
проект на своей платформе; сборка по хешам с высокой вероятностью упала бы
у него. Для промышленного развёртывания рекомендуем закрепление по
хешам, базовый образ по digest и приватное зеркало — три меры, каждая из
которых уместна, когда сборка идёт в известном контуре. На неизвестной машине
рецензента они мешают.

### 5.8 Исчерпание ресурсов хоста

**Периметр.** Индексация корпуса — самая тяжёлая операция: замерено 12 минут 36
секунд и 1.4 ГБ пика на 469 страницах. Без ограничений контейнер способен
вытеснить с машины соседей.

**Что задаётся командой запуска.** `--memory 6g --cpus 4` в рекомендованной
команде. Значения взяты с запасом к замеренному пику.

**Альтернативы.** Без ограничений — принято по умолчанию. Квоты оркестратора
(requests/limits в Kubernetes) — правильный путь при промышленном
развёртывании. Вынос индексации в отдельную разовую задачу — снимает пик с
обслуживающего контейнера совсем.

**Почему так.** Ограничения на уровне контейнера — минимальная мера, доступная
без оркестратора. Третий вариант считаем правильным и вынесли его в список
улучшений: индексация по природе разовая операция, и держать под неё память в
сервисе, который отвечает на вопросы, незачем.

### 5.9 «Здоров» означало «поднялся веб-сервер», а не «работает»

**Периметр.** Не угроза извне, а свойство самой поставки: контейнер сообщал
докеру своё состояние, и сообщал неверно. Проверка живости открывала страницу
Streamlit и на этом заканчивалась. 26.08.2026 контейнер поднялся здоровым за
десять секунд с чистым журналом и не работал вовсе — кэш модели эмбеддингов
метил в домашний каталог при файловой системе, смонтированной только для чтения.
Отказ вскрылся при первом вопросе пользователя, то есть тогда, когда проверять
было уже поздно. В промышленном контуре цена выше: оркестратор считает такой
контейнер исправным и направляет на него нагрузку.

**Что сделано в поставке.** Проверка трогает оба узла, на которых стои́т работа:
хранилище (открылось ли, сколько в нём фрагментов) и эмбеддер (считает ли он
вектор). Дорогую часть — загрузку модели — делает один раз сам процесс
приложения, при старте, в фоне; результат кладётся отметкой в каталог данных.
Частая проверка живости читает страницу и эту отметку и стоит миллисекунды.

Три решения внутри стоит назвать, потому что каждое можно было принять иначе.

*Проверка зовёт тракт, а не повторяет его.* В `neftegaz/health.py` нет ни своего
клиента хранилища, ни своего вызова библиотеки эмбеддингов: берётся тот же
объект, что отвечает на вопросы пользователя, с теми же настройками и тем же
кэшем. Копия тракта отстала бы от него молча — она не подаёт признаков
устаревания.

*Отсутствие отметки — это «не готов», а не «здоров».* Нечитаемая или неполная
отметка приравнивается к отсутствующей. Обратное решение превратило бы порчу
файла в зелёный свет и повторило бы исходную ошибку.

*Прогрев идёт фоном и не является условием старта.* Иначе контейнер при
недоступной сети не поднимался бы вовсе, а сейчас он поднимается и объясняет
беду в интерфейсе. Пока прогрев не закончен, проверка честно отвечает «ещё не
готов»; период ожидания поднят с 40 секунд до 5 минут, потому что при первом
запуске модель качается (241 МБ), и прежнее значение объявляло бы контейнер
больным на каждом первом старте.

**Замер.** Три класса отказа: процесс не поднялся; страница отвечает, но
хранилище не открывается; страница отвечает, но эмбеддер не грузится. Прежняя
проверка различала 1 из 3, новая — 3 из 3, и каждая причина названа отдельно:
администратору видно, чинить ему том с данными или кэш модели. Отрицательный
контроль: на исправной системе проверка по-прежнему говорит «здоров» — проверка,
красная всегда, не лучше отсутствующей.

### Что из этого проверяется, а что заявляется

Меры 5.1, 5.2, 5.3, 5.5, 5.6, 5.7, 5.8 и 5.9 находятся в поставке. Часть из них
проверяется чтением репозитория, часть — прогоном на работающем контейнере:

```bash
docker compose exec analyst sh scripts/check_hardening.sh   # шесть строк, код 0/1
ss -ltn | grep 8501                                         # на ХОСТЕ: 127.0.0.1:8501
```

Вторая строка стоит отдельно потому, что публикация порта изнутри контейнера не
видна вовсе: контейнер не знает, на какой интерфейс хоста его выпустили.

Мы намеренно приводим здесь проверки. Непроверенный периметр остаётся
намерением, а проверка, отвечающая одно и то же при работающей и при отключённой
защите, не стоит ничего.

Каждая проверка подобрана так, чтобы отвечать по-разному при применённой и при
забытой мере, и это замерено запуском контейнера в обоих режимах: без флагов —
ноль из шести, со всеми мерами — шесть из шести. Соблазн взять более очевидные
проверки мы называем, потому что сами в него попали. `CapEff` пуст, а запись в
`/etc` запрещена уже у непривилегированного пользователя: при забытых флагах
запуска обе проверки отвечают то же самое. Про снятые возможности говорит
ограничивающий набор `CapBnd`, а про неизменяемую ФС — попытка записи туда, куда
пользователь писать вправе.

**Что осталось рекомендацией и почему именно это.** Пять мер не переводятся в
поставку без предположений о чужой инфраструктуре, и мы называем их поимённо,
чтобы список «сделано» не выглядел полным: egress-прокси в режиме белого списка
(5.4), секреты оркестратора вместо переменных окружения (5.2), корпоративный SSO
через обратный прокси (5.6), закрепление зависимостей по хешам и базового образа
по digest вместе с приватным зеркалом индекса (5.7), вынос индексации в отдельную
разовую задачу (5.8). Первые три требуют сетевого контура и служб заказчика.
Четвёртая — сознательный размен в пользу проверяющего: сборка по хешам с высокой
вероятностью упала бы на его машине, и это объяснено в 5.7. Пятая — вопрос
оркестрации, а не образа.

## 6. Ограничения текущей реализации

1. **Корпус — только EIA.** ОПЕК отдаёт MOMR через форму (прямой запрос
   получает HTTP 403), IEA OMR — платный продукт. Скрипт загрузки об этом
   пишет; оба источника добавляются копированием PDF в `data/reports/` с
   соблюдением конвенции имени. Ограничение в доступе, не в коде.

2. **Словарь для поиска по словам покрывает 22 гнезда терминов.** За их
   пределами русский запрос опирается только на вектор. «Urals», «коэффициент
   загрузки НПЗ», «фьючерсный контракт» переводятся, более узкая номенклатура —
   нет.

3. **Структура таблиц не разбирается.** Нарезка строк по точкам-выноске
   вытягивает отдельные строки, но колонок не знает: сопоставление значения с
   кварталом делает модель, читая шапку. На проверенных сценариях она делает
   это верно, но гарантии тут нет — это остаётся зоной, где ошибка возможна и
   не будет поймана автоматически.

4. **Эластичность измерена на девяти кварталах, и это мало.** Она больше не
   литературная константа (§3.13): короткий конец оценивается по рядам корпуса,
   и коридор расширяется на ширину доверительного интервала оценки. Но
   наблюдений девять, добыча экзогенна не полностью, а длинный конец не измерен
   вовсе — корпус накрывает полтора года.

5. **Прогноз по факторам ограничен горизонтом чужого прогноза.** Регрессия по
   факторам реализована и стоит третьим методом (§3.13), но ряды берутся из
   корпуса STEO: дальше последнего прогнозного квартала EIA метод отказывается
   считать, а ошибка EIA в добыче становится нашей ошибкой в цене.

6. **Качество ответа определяется подключённой LLM.** Маршрутизация, поиск и
   расчёты работают одинаково, но формулировка и точность переноса чисел
   зависят от модели.

7. **Кросс-языковой поиск на облегчённой модели.** Умолчание выбрано ради
   быстрого первого запуска; `intfloat/multilingual-e5-large` заметно точнее
   ценой 2.2 ГБ и вчетверо более долгой индексации. Переключается одной строкой
   в `.env`.

8. **Память диалога не переписывает запрос для поиска.** Ходы помнятся и едут в
   промпт, но в поиск по корпусу и в веб уходит вопрос как есть: по строке
   «а на пять лет?» корпус не находит ничего.

9. **Время ответа.** Сложные сценарии занимают 60–145 с. Разброс между
   прогонами при неизменном коде достигает четырёхкратного (58–235 с на одном
   и том же вопросе) — это поведение LLM, не логики агента.

## 7. Что улучшили бы при большем времени

★**Этот раздел — выжимка, а не самостоятельный список.** Полный перечень живёт в
`docs/РЕЕСТР-РЕШЕНИЙ.md`: у каждого принятого решения там есть поле «потенциал
пересмотра», где названы адресат (мы или заказчик), выигрыш, цена, что при этом
ломается и при каком условии за это стоит браться. Приложение Б реестра
выстраивает их в очередь по ШИРОТЕ КАСАНИЯ — от «добавить запись туда, где уже
есть такие же» до «требуется согласие заказчика».

Два параллельных списка неизбежно разошлись бы, и разошлись бы молча: правку
вносят в один, а читают другой. Поэтому здесь — десять пунктов верхнего уровня
со ссылками на номера записей, а подробности к каждому — в реестре.

**Можем сделать сами, касается одного модуля или общего правила:**

1. **Переранжирование парной моделью** (Р-042). Поиск возвращает кандидатов,
   переранжировщик перечитывает их вместе с запросом. На отчётах со множеством
   похожих таблиц это обычно даёт больший прирост, чем смена модели
   эмбеддингов. Цена — вес образа и задержка на каждом запросе.

2. **Переписывание запроса по контексту разговора** (Р-059) для поиска в
   корпусе и в вебе. Память диалога сделана (§3.15), но в поиск уходит вопрос
   как есть: по строке «а на пять лет?» корпус не находит ничего.

3. **Двухъярусная шапка таблицы, проведённая до пар «столбец = значение»**
   (Р-029). Сняла бы с модели сопоставление значения с колонкой — единственное
   место, где сейчас возможна ошибка, которую наша приёмка не поймает.

4. **Расширение словаря предметной области** (Р-043) — по частотному списку
   запросов заказчика; альтернатива (перевод запроса моделью) стоит задержки на
   каждом запросе и ещё одного режима отказа.

5. **Текст роли и реплика отказа — в настройку** (Р-052, Р-069). Сейчас тон
   ответов правится только правкой кода.

**Требует пересборки индекса и перегенерации демонстраций:**

6. **Крупная модель эмбеддингов умолчанием** (Р-008) — и обязательно вместе с
   ней перемер порога близости (Р-044): косинусы разных моделей несопоставимы,
   перенесённый вслепую порог либо зальёт контекст, либо молча опустошит выдачу.

7. **Расширенный эталон стенда разборщиков и решение о замене читателя**
   (Р-020, Р-021). Без расширенного эталона выбор между двумя разборщиками
   сделать нечем, а он — фундамент всей проверяемости (§3.8).

**Зависит от заказчика:**

8. **Расширение корпуса вглубь истории** (Р-012). Снимает разом три названных в
   §6 ограничения: ширину доверительного интервала эластичности,
   неразличимость горизонтов и невозможность третьего регрессора. Требует не
   работы, а доступа к подпискам.

9. **Уровень запасов третьим регрессором** (Р-081, Р-075). При полных
   хранилищах тот же шок предложения двигает цену слабее, и сейчас модель этого
   не различает. Строго после расширения корпуса: на девяти наблюдениях третий
   регрессор добавлять нельзя.

10. **Решение о хранении переписки на диске и срок её хранения** (Р-056).
    Настройка есть и работает в обе стороны (§3.15); чего нет — срока хранения
    и удаления по нему. Это вопрос службы безопасности заказчика, а не наш.

**Исполнено с прошлой редакции этого раздела** — пункты, стоявшие здесь и
закрытые:

* **Ступень достоверности доведена до текста ответа** (Р-036, Р-066): пометка
  стои́т внутри ссылки и говорит читателю, что с ней делать (§3.9).
* **Сверка цитат вошла в автоматическую приёмку** (Р-107): раньше инструмент
  запускался вручную, то есть проверялся дисциплиной запускающего (§4).
* **Настройки проверяются при старте** (Р-014), а не при первом использовании:
  опечатка меняла поведение молча (§4).
* **Правило «поля-однодневки сбрасываются каждый ход» исполняет машина**
  (Р-067): словами оно было записано и не сработало трижды (§4).
* **Разрыв между знаками и токенами измерен** (Р-047): полный переход бюджетов
  в токены по-прежнему открыт, но окно модели теперь можно назвать настройкой,
  и несоответствие выясняется при старте (§3.15).

## 8. Об использовании Ouroboros

В этой поставке Ouroboros не использован. Развернуть цикл самоперестраивающегося
агента, обеспечить его изоляцию и получить предсказуемый результат в отведённое
время мы не успевали, и выбор был сделан в пользу работающего продукта.

Ответ на вопрос задания у нас при этом есть, и опирается он на опубликованные
работы самого заказчика.

### Условие, при котором самоулучшение окупается

Команда STARM (Ю. Шахвалиева, 12.08.2026) сформулировала это как
закономерность: итеративное самоулучшение даёт прирост там, где есть дешёвый
проверяющий — судоку, арифметика, — и не даёт его там, где проверяющего нет,
например на ARC-AGI. Причину авторы называют прямо: рекурсивные модели рассуждения
плохо находят собственные ошибки.

Отсюда рабочий критерий применимости. Ouroboros окупается на задаче с машинной
приёмкой и простаивает на задаче, где приёмку выносит человек или языковая
модель.

Поставляемая система этому условию удовлетворяет. У неё пять сотен тестов и
`scripts/check_citations.py`, который проверяет, что каждое число в ответе
подтверждено ссылкой на источник, и сообщает результат кодом возврата. Это
готовый машинный вход для приёмки изменений.

Два места, где мы применили бы Ouroboros в производстве этой системы:

1. **Параметры конвейера поиска** — размер фрагмента, перекрытие, число
   кандидатов, порог отсечения. Пространство перебора большое, ручной перебор
   дорог, приёмка полностью машинная: доля подтверждённых чисел и прохождение
   тестов.

2. **Словарь предметной области** (§7, п. 3). Это множество мелких правок с
   немедленно измеримым эффектом на выдачу поиска.

Встраивание в рантайм конечного решения мы из рассмотрения исключаем
сознательно. Для регулируемой отрасли компонент, переписывающий себя между
запусками, требует отдельного контура контроля, и это самостоятельная
инженерная задача.

### Что в этом классе систем уже сделано

Целевая функция при самомодификации новизной не является. К августу 2026 её
реализовали по меньшей мере пять систем: ADAS (08.2024), SICA (04.2025),
Darwin Gödel Machine (05.2025), AlphaEvolve (05.2025), SEAL (06.2025). Darwin
Gödel Machine пошла дальше и опубликовала собственный пойманный взлом метрики:
узел архива удалил маркеры детектора галлюцинаций и получил за это идеальный
балл.

Ouroboros в этом ряду занимает отдельную позицию. В своей статье автор относит
Darwin Gödel Machine к подходам с отбором по бенчмарку и противопоставляет ей
контур ревью языковыми моделями. Отбора по замеру у него нет намеренно.

### Что не решено ни в одной из них

Мы разобрали шесть систем этого класса по исходному коду. Два места остались
пустыми у всех.

**Отзыв уже принятого изменения.** То, что называется откатом, устроено как
невыбор ветки в архиве, который только растёт. Изменение, принятое ошибочно,
остаётся в родословной всех последующих. У SEAL отзыв невозможен физически:
веса перезаписаны.

**Провенанс приёмочного решения.** Архив хранит число — `accuracy_score`,
`fitness`, содержимое `perf.json`. Вывод, из которого это число получено, он не
хранит. На вопрос «против какой версии метрики измерено и не устарел ли замер»
ответить нечем.

Ouroboros устроен богаче остальных в этом ряду, и это стоит сказать прямо. У
него есть отпечаток цели (`evolution_fingerprint.py`), чекпойнты исхода цикла и
слепок способности решать задачи (`evolution_checkpoints.py`), учёт авторства
изменений (`mutation_attribution.py`) и полноценный откат
(`tools/git_rollback.py`, `supervisor/update_recovery.py`).

Критерий у него тоже есть, и он уже не скаляр. В `post_task_evolution.py`
решение о запуске цикла принимается по текстовому заданию, и в нём записаны
условия обоих родов.

Приоритеты: предпочитать пункты из бэклога; взвешивать историю, где классы
целей с приживавшимся исходом дают лучшую ставку; склоняться к малым точечным
целям и избегать широких переработок.

Запреты: не предлагать заново закрытое или отброшенное; не предлагать заново
активную цель кампании.

Пустое место в другом. Критерий записан прозой, а вердикт по нему выносит
языковая модель того же семейства, что и сам агент. Автор Ouroboros называет
этот риск сам: «LLM-ревьюеры могут разделять слепые зоны с основным агентом».
И вердикт не сохраняется как вывод — только как исход. Поэтому откат остаётся
действием оператора и не может стать следствием переоценки после применения.

### Во что эта пустота обходится на измеримом примере

`harness-bench-fast` (С. Тращенков, ai-forever) — стенд из 391 задачи, где приёмку
выносят состояние файлов, тесты и SQL-запросы. Авторы обозначают это как
«детерминированная верификация, не LLM-судьи». Профиль `deepagents-gigachat` даёт на
нём GigaChat 3.5 рост с 302/391 (77.2%) до 340/391 (87.0%) при сокращении
расхода токенов на 41%.

Версия профиля 0.0.4 добавила в критерий приёмки ограничение — проверку
воспроизводимости вывода. На GigaChat 3.5 это дало ещё 10.8 задачи в среднем
по прогонам. На GigaChat-3.1-10B то же ограничение стоило 14.5 процентных
пункта. Доля прогонов, упирающихся в лимит шагов, выросла там с 3.6% до 33.6%.
Причина в поведении агента: получив отказ без причины, он повторяет
заблокированное действие, пока не исчерпает бюджет. Авторы советуют закреплять
предыдущую версию профиля для моделей, которые не умеют действовать по отказу
инструмента.

Ограничение в критерии дало меньше, чем стоил отказ, не несущий причины. Стек
здесь тот же, что у нас: Deep Agents на LangGraph.

### Направление, которое мы предлагаем к проверке

Соединить три вещи, две из которых уже принадлежат заказчику.

1. `harness-bench-fast` как измеренный вход приёмки вместо кворума языковых
   моделей. Судья остаётся языковой моделью, но на вход ему приходит измеренное
   число.

2. Тот же критерий, что уже написан в `post_task_evolution.py`, но как данные:
   приоритеты и запреты в явном виде, отдельно от текста запроса, с версией.
   Сочинять его не придётся — он там есть, и оба вида условий в нём уже сидят.

3. Вывод вердикта логическим движком с провенансом, чтобы отказ нёс причину, а
   принятое изменение можно было отозвать, когда опора вердикта изменилась.

Точка встраивания узкая. Решение принимает `_decide_promotion` и возвращает
структуру из четырёх полей; подпись функции и форма ответа сохраняются,
меняется способ получения вердикта. Супервизор и транзакционный слой при этом
не затрагиваются.

Проверку мы уже собрали — стенд, где тот же критерий записан правилами и
вердикт приходит с доказательством. Сценарий взят из комментария в самом
Ouroboros: закрытая цель предлагалась заново четыре-пять раз, и починкой стало
добавить список закрытых в текст запроса. На стенде такой отказ выглядит так:

```
ОТКЛОНЕНО fp_c — закрыта-или-отброшена (p=1.000)
   потому что: candidate('fp_c',) И closed('fp_c',)
```

Стенд стоит на неизменённом Scallop, включает три отрицательных контроля и
может быть передан по запросу. Главный контроль снимает один-единственный факт
«цель закрыта» и требует, чтобы цель стала допустимой: без этого работающий
запрет неотличим от отказа по любой посторонней причине.

Третий пункт — область, в которой у нас есть собственная наработка. Проверяемым
вкладом мы считаем именно его; идея целевой функции при самомодификации нам не
принадлежит.

**Статус раздела.** Изложенное здесь — направление развития и предмет
отдельного POC. В сдаваемую систему оно не входит и на её работу не влияет.

### Чего мы не утверждаем

Мы не запускали Ouroboros на этой задаче. Оценка окупаемости выведена из
условия STARM и свойств нашей приёмки, и проверяется прогоном.

Пустоты в классе установлены чтением кода шести систем. Своего эксперимента за
этим утверждением нет, и выборка ограничена этими шестью.

Прирост от предлагаемого соединения не измерен. Стенд показывает, что вердикт
и его доказательство получаются, и что запрет держит; насколько это улучшает
сами циклы самоулучшения, покажет только прогон Ouroboros с этим решением и без
него.

## Приложение. Как воспроизвести замеры

Команды разделены по месту запуска, и это различие не формальность: образ несёт
только то, что нужно работающей системе, поэтому тестовые зависимости в нём
отсутствуют намеренно.

**Из репозитория, в виртуальном окружении** (`pip install -r requirements.txt`
плюс `pytest`):

```bash
python -m pytest tests/ -q                  # весь набор тестов, ~105 с
python scripts/build_index.py               # сборка индекса, ~12 мин, пик 1.4 ГБ
python scripts/run_demo.py                  # демо-сценарии, перезаписывает demo/
python scripts/check_citations.py           # 0 — чисто, 1 — находка, 2 — не отработала
python -m neftegaz.rag.intake data/reports  # осмотр файлов, числа раздела 3.7
python -m neftegaz.rag.crosscheck data/reports  # сверка путей чтения, числа раздела 3.8
```

Обе последние команды печатают сводку по каждому файлу и принимают как каталог,
так и отдельный PDF.

**В работающем контейнере** — сверка цитат по транскриптам, которые едут в
образе:

```bash
docker exec <контейнер> python scripts/check_citations.py
```

Ожидается: 45 сверенных чисел, ни одного неподтверждённого, ни одного без
ссылки, четыре числа из веба помечены как непроверяемые; код возврата 0.

**Меры защиты — там же, и опыт ставится дважды**, иначе он ничего не различает:

```bash
docker compose exec analyst sh scripts/check_hardening.sh   # ожидается 6 из 6, код 0
# и для сравнения — запуск без единого флага:
docker run --rm -v "$PWD/data:/app/data" neftegaz-analyst sh scripts/check_hardening.sh
# ожидается 0 из 6, код 1
```

Смысл второй команды в том, что проверка, дающая одинаковый ответ при
применённых мерах и без них, не проверяет ничего. Здесь ответы разные, и это
замерено, а не заявлено (раздел 5.3).

Замеры времени и памяти получены на рабочей станции с Ryzen 7900X при
ограничении в 12 потоков; абсолютные значения зависят от машины, соотношения —
нет.
